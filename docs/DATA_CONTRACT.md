# Данные, расчёты и структура BakePlan

Контракт опубликованного приложения; быстрый запуск — в [README](../README.md). ML и оценка описаны отдельно в [ML_INTEGRATION](ML_INTEGRATION.md) и [EVALUATION](EVALUATION.md).

## CSV v1

UTF-8, разделитель запятая, ISO-дата `YYYY-MM-DD`, обязательные столбцы:

```csv
date,product_id,is_open,opening,produced,sold,waste,closing,other_out,stockout_status
2026-10-05,p1,true,0,100,80,20,0,0,none
```

`product_id` — строковый стабильный ключ p1…p5, название не ключ. `is_open`: true/false или1/0. Количества — неотрицательные целые не более 1 000 000 000; более узкие ML-границы указаны в руководстве. Баланс: opening+produced=sold+waste+closing+other_out. `stockout_status`: none/occurred/unknown; closing0 после waste не доказывает дефицит. Дубликат дата/товар, неизвестный товар, дробь, отрицательное число или неверный баланс отклоняются. Пропуск не становится продажей0; закрытый день задаётся явно. Каталог фиксирован в `backend/config.py`; смена каталога требует новой версии и проверки контракта.

B0 берёт только пригодный день ровно за7 календарных дней. B1 усредняет до4 последних пригодных таких же дней недели за56 дней. Пригодность: открыто, stockout none, дата не позже среза. Источники и число наблюдений сохраняются. Недостаточная история помечается; без истории выдаётся ручная заготовка0, а не прогноз0. Округление к ближайшей партии, равное расстояние вниз; затем ограничение максимальной разрешённой партией. Прогноз, рекомендация и подтверждённый выпуск хранятся отдельно. Общую загрузку печи управляющий проверяет вручную. Денежной оптимизации нет: затраты неизвестны.

Наборы неизменяемы. Поддерживаемые schema_version — history-1 (по умолчанию) и отдельная sales-1; неизвестная версия отклоняется. Повтор одинакового CSV с теми же source, schema_version и явно указанными bakery_id/target/unit/provenance возвращает существующий dataset_id (HTTP200); новый импорт — HTTP201. Исправления содержимого получают новый набор. План хранит снимок версии данных и параметров. Подтверждение атомарно; revision защищает от устаревшего экрана, idempotency_key возвращает исходный результат при повторе того же запроса и конфликтует при изменённом теле. Прошлые редакции доступны через API. Бизнес-данные, SQLite и секреты исключены из Git. Не загружайте pickle/joblib; поддерживается только CSV.

## Контракт и структура после рефакторинга

`backend/imports.py` — общий строгий CSV, `forecasting.py` — чистые B0/B1; `planning.py` — партии и допуск автоматической рекомендации; `services.py` — прикладные сценарии, `storage.py` — SQLite и миграция, `schemas.py/config.py` — вход и каталог. Подтверждение сохраняет один BEGIN IMMEDIATE: повторный ключ проверяется до даты/revision, затем результат, снимок и редакция записываются вместе. Frontend разделён на import/planning/history, типы и API-клиент; Redux и ORM не добавлялись.

Численный baseline использует пригодные открытые дни stockout=none и активные даты каталога. Перенос opening/closing среди наблюдаемых открытых дней за56 дней или stockout/unknown более50% отключает автоматическую рекомендацию, но диагностический baseline сохраняется. Offline использует то же численное ядро, но явно исключает opening>0 из эксперимента; closing>0 сам по себе не исключает численную оценку продаж. Эти политики также действуют при явном выборе ML в рабочем плане. Каталог API разрешает только p1…p5; offline допускает другие строковые ID и сам задаёт период исторической оценки. Формат/баланс/закрытый день проверяются одинаково.

Списки `GET /api/datasets` и `GET /api/plans` возвращают краткие метаданные без rows/items; limit по умолчанию20, максимум100, offset>=0. Порядок — устойчивый порядок создания (последние первыми); новый импорт/план может сдвинуть offset, обновите первую страницу. Детали: `/api/datasets/{id}` и `/api/plans/{id}`. В UI есть следующая/предыдущая страница истории.

Ошибки имеют JSON `error: {code, message, details}`, включая413 при теле больше2МБ. API-клиент также показывает безопасное сообщение для не-JSON ответа прокси. Строка CSV ограничена1млн символов, максимум10000 записей; закрытый день с ненулевыми produced/sold отклоняется обеими реализациями.
