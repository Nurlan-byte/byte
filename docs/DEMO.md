# Демонстрация примерно за 90 секунд

Только синтетические данные `fixtures/synthetic_demo.csv`, созданные для проекта: пять изделий, 56 календарных дней, никаких исходников реальной пекарни. Не называть этот файл реальными продажами и не показывать синтетический MAE как точность продукта.

## Подготовка до записи

Стартовый экран — «План». Разделы «Данные», «Модель» и «История» доступны в постоянной навигации. Заголовок показывает выбранную дату, а не всегда «завтра»; прошедшая/текущая дата помечена историческим воспроизведением. B1 остаётся методом по умолчанию, обучение ML необязательно.

- Чистый запуск по README, отдельная демонстрационная SQLite. Убедиться в `/api/health` и записать commit.
- Открыть «Данные» → «Загрузить демо CSV», импортировать с source `synthetic`, bakery `demo`, происхождением «Синтетическая демонстрация BakePlan».
- Для согласованного двухдневного горизонта: дата плана/прогноза `2026-10-13`, срез `2026-10-11`. Для сегодняшней записи после 13 октября это явно историческое воспроизведение.
- Обучить модель заранее: дождаться статуса и проверить каждый товар. Если модель не готова, показать честный B1 и причину, не менять подпись на ML.
- Рассчитать план, проверить допустимые партии. Заранее проверить экспорт, перезагрузку и рестарт на той же БД. Не выдавать этот чек-лист за выполненную ручную QA.


## Отдельная чистая база для репетиции

«Начать заново» здесь означает выбрать новый путь, а не удалить прежнюю SQLite. Сначала остановите API через Ctrl+C и запишите его прежний `BAKEPLAN_DB`. Команды выполняются из корня проверенного checkout с уже установленными зависимостями. Старые `.sqlite3`, `-wal`, `-shm` и резервные копии не трогаем. В интерфейсе после запуска обновите страницу и выберите новый импорт; не используйте сохранённые ID предыдущей базы.

Windows PowerShell, нативный запасной запуск:

```powershell
$demoDir = Join-Path (Join-Path (Get-Location) "data") ("defense-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $demoDir -ErrorAction Stop | Out-Null
$env:BAKEPLAN_DB = Join-Path $demoDir "demo.sqlite3"
Write-Host "Новая демонстрационная БД: $env:BAKEPLAN_DB"
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Linux, нативный запуск:

```sh
mkdir -p data
demo_dir=$(mktemp -d "$PWD/data/defense-XXXXXXXX") || exit 1
export BAKEPLAN_DB="$demo_dir/demo.sqlite3"
printf 'Новая демонстрационная БД: %s\n' "$BAKEPLAN_DB"
.venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Frontend запускается отдельно по [README](../README.md#быстрый-запуск). Для повторного открытия этого же дубля используйте **напечатанный путь**, а не выполняйте генерацию нового каталога. Для рестарта проверки также оставьте тот же путь. Для возврата к рабочей базе остановите demo API и восстановите ранее записанный `BAKEPLAN_DB`. Не меняйте путь у работающего сервера и не копируйте живую БД.

Для Docker используйте [LOCAL_WINDOWS](LOCAL_WINDOWS.md) и его отдельный project/volume. Приведённые выше команды относятся только к нативному процессу; они не переключают БД контейнера. Не применяйте `down --volumes`, factory reset или volume prune ради чистого дубля. Если Docker-демо уже содержит важные данные, сначала сохраните и проверьте backup по инструкции; до отдельного выбора нового имени БД используйте нативную чистую демонстрацию.

## Точная последовательность ручной репетиции

Это checklist для выполнения на целевом компьютере, а не заявление о уже пройденной ручной QA. Основной сценарий всегда использует цель `2026-10-13` и срез `2026-10-11` (t−2). Старый пример B1=65 и рекомендации 60 на `2026-10-12` относится к другой контрольной точке и в этот показ не включается.

1. Запустите отдельную чистую demo SQLite по инструкции выше. Откройте «Данные» и нажмите «Загрузить демо CSV», проверьте источник `synthetic`, пекарню `demo` в «Параметры набора» и физические штуки; для совпадения с replay замените автозаполненное происхождение на «Синтетическая демонстрация BakePlan», затем «Проверить и импортировать». Ожидается 280 строк и период 17.08.2026–11.10.2026. Исходный CSV скрыт в «Вставить или проверить CSV»; сохранённый источник и период остаются видны. Переключение разделов сохраняет черновик в этой вкладке.
2. **До обучения** через навигацию «Модель» задайте срез `2026-10-11`, дату `2026-10-13`, «Метод диагностики» = ML. Нажмите «Получить прогноз». Ожидайте фактический B1 и причину отсутствия модели; для p1 отображается `26.0`. Запишите этот отдельный резервный фрагмент сейчас.
3. Нажмите «Обучить модель» с тем же срезом, дождитесь ready и проверьте все пять товаров. Снова нажмите «Получить прогноз»: фактический метод ML, p1 отображается `29.8`. В оценке видны MAE `0,416667` для B1 и `0,767225` для ML, парное N=60 и покрытие 60/60. Чем меньше MAE, тем лучше; интерфейс прямо сообщает, что здесь ML хуже B1.
4. Откройте «План» и отдельно проверьте дату `2026-10-13`, срез `2026-10-11`, открытый целевой день и «Базовый метод» = ML. Нажмите «Рассчитать план». Для p1 прогноз `29.8`, рекомендация 24; остальные рекомендации 30/32/36/36.
5. В «Количество Хлеб пшеничный» замените 24 на 84. Остальные количества оставьте без изменений. Нажмите «Подтвердить и сохранить». Проверьте «Сохранено: 84 шт.», статус «Подтверждён» и версию 1. ID плана находится в «Технические данные плана». Это пример ручного управления, не совет выпекать 84 штуки.
6. Обновите страницу, откройте «История» → «Обновить историю» → «Открыть план» у нужной даты и экспортируйте CSV. Источник и статус подписаны по-русски, ID и raw-статус доступны в деталях. Проверьте пять строк, target/cutoff, метод ML, p1 forecast=`29.7621242495623`, recommended=24, confirmed=84. Отдельно выполните настоящий перезапуск API с тем же путём SQLite и повторите чтение, если собираетесь утверждать сохранность после рестарта на этом компьютере.
7. **После сохранения плана** откройте «Данные», загрузите `fixtures/invalid_balance.csv` и нажмите «Проверить и импортировать». Ожидается понятный отказ из-за баланса (API 422/INVALID_CSV). Вернитесь в историю: тот же ID плана, подтверждённые 84 и экспорт должны сохраниться. Это проверка отсутствия потери уже сохранённого состояния; не очищайте базу между шагами 5–7.

Для основного 90-секундного дубля модель уже подготовлена; fallback и ошибочный импорт снимаются дополнительными фрагментами. Полный прогон со временем обучения не обязан укладываться в 90 секунд.

## Текст шести слайдов

### Слайд 1. Как пекарне подготовить выпуск на завтра

BakePlan помогает владельцу небольшой пекарни составить план по пяти изделиям.

- История продаж и товарный баланс в одном CSV.
- Прогноз и рекомендация с учётом партии и предела выпуска.
- Владелец проверяет, корректирует и подтверждает план.

Цель пилота: проверить, помогает ли такой процесс планировать выпечку. Сокращение списаний и денежная экономия пока не доказаны.

### Слайд 2. Что уже работает

CSV → проверка → обучение при достаточной истории → прогноз → допустимый план → ручное подтверждение → история и экспорт.

- Ошибочный баланс или дубликат отклоняет весь импорт.
- Прогноз, рекомендация и подтверждённый выпуск хранятся отдельно.
- Данные, модели и планы сохраняются в SQLite.

На показе используются вымышленные данные: пять изделий, 56 календарных дней.

### Слайд 3. Как устроен прогноз

- B1: средние продажи в последние четыре подходящих одноимённых дня недели, найденные в пределах 56 дней.
- ML: B1 с поправкой, которую обучает Ridge, α = 100.
- Признаки: доступная история продаж, лаги, скользящие средние, день недели.
- Нет пригодной ML-модели: явно показываем B1; нет подходящей истории: нужен ручной план.

Для цели t используем завершённые факты только до t−2. Это допущение о готовности учёта нужно подтвердить с пекарней.

### Слайд 4. Решение остаётся у владельца

- Пять фиксированных изделий, размер партии и дневной предел каждого.
- Закрытый день: выпуск 0.
- Перенос остатков или частый дефицит/неизвестное наличие отключают автоматическую рекомендацию.
- Общую загрузку печи и итоговые количества проверяет человек.

Пример: пшеничный хлеб, партия 12, предел 100 штук. Наибольший допустимый выпуск — 96; ручной вариант 84 допустим.

### Слайд 5. Что подтверждено и что предстоит проверить

Подтверждаем работу программы на синтетических сценариях и автоматизированных проверках. Состояние CI проверяем по точному SHA.

Для сравнения B1 и ML используем одинаковые пары «дата × товар» и одинаковый горизонт. Показываем MAE, число пар, покрытие и исключения. На синтетическом примере MAE модели выше, чем у B1; преимущества ML здесь нет.

Реальная точность, неудовлетворённый спрос, снижение списаний и экономия пока не измерены. Следующий шаг — разрешённые данные одной пекарни и заранее зафиксированный будущий период проверки.

### Слайд 6. Команда и следующий шаг

- Нурлан: модель, Python API и хранение.
- Бага: интерфейс.
- Диас: независимая проверка и воспроизведение.
- Асыл: источник данных, разрешения и границы пилота.

Ближайшие действия: ручная проверка на целевом ноутбуке, резервная видеозапись и согласование данных пилота.

Текущий MVP: одна пекарня, пять изделий, локальный доверенный запуск. Публичный хостинг, аккаунты и изоляция пользователей не готовы.

Примечание для докладчика: стартовый код создан с помощью Codex. Это раскрыто в CONTRIBUTING.md. Требования конкурса к AI-инструментам и составу сдачи ещё нужно подтвердить у организатора; не утверждать, что допуск уже получен.

## Речь примерно на 90 секунд

«BakePlan помогает небольшой пекарне подготовить выпуск на завтра. В нашем MVP пять изделий, а окончательное решение принимает владелец.

На экране вымышленные данные за восемь недель. Загружаем CSV: программа проверяет формат, дубликаты и товарный баланс. Пропущенный день не превращается в нулевые продажи.

Для этого набора модель уже обучена. Простой ориентир B1 усредняет продажи в последние подходящие одноимённые дни недели. Наша экспериментальная модель добавляет к нему поправку Ridge. Она использует только доступную историю. Если модель не готова, интерфейс показывает B1 и причину перехода.

В оценке сравниваем B1 и ML на одинаковых датах и показываем число наблюдений и покрытие. На этом синтетическом примере ML хуже B1.

Эта демонстрация подтверждает работу программы. Реальную точность и влияние на списания предстоит проверить с пекарней. Следующий шаг — разрешённая история и будущий период проверки по заранее согласованным правилам».

## Восемь сложных вопросов жюри

### 1. Где здесь AI и зачем он, если есть простое среднее

Встроена обучаемая Ridge-регрессия, которая корректирует B1 по признакам истории. B1 остаётся прозрачной точкой сравнения и резервным методом. На текущем синтетическом holdout ML даже хуже B1: MAE 0,767225 против 0,416667 на 60 общих парах. Эти числа проверяют воспроизведение, не качество на реальной пекарне. Преимущество нужно проверять на одинаковом будущем периоде. Если ML хуже или часто недоступен, это будет результатом проверки, а не поводом скрыть B1. Соответствие конкурсной категории AI подтверждается правилами организатора, ответа пока нет.

### 2. На каких данных обучались и откуда они

В демонстрации используем созданную для проекта синтетику: пять изделий и 56 дней. Она позволяет проверить импорт, обучение, fallback и сохранение, но не доказывает точность для пекарни. Ранее команда исследовала внешний sales-only набор BreadBasket. Его товарные строки не равны физическим штукам; старый просмотренный test и улучшение 3,35% не являются метрикой нынешней интегрированной модели. Для пилота нужны разрешённые агрегаты конкретной пекарни с понятными единицами и балансом.

### 3. Если хлеб закончился, продажи ведь ниже спроса. Как это учитывается

Да. Модель прогнозирует наблюдаемые продажи и не восстанавливает потерянный спрос. Для физического учёта дни с дефицитом или неизвестным наличием исключаются из обучающих меток. Также исключаются закрытые дни и дни с переносом остатков. Если более половины наблюдаемых открытых дней за используемое окно имеют дефицит или неизвестное наличие, автоматическая рекомендация отключается. Перенос остатков тоже требует ручного плана. Нулевой остаток не считается доказательством отсутствия дефицита.

### 4. Какова точность и как вы исключили заглядывание в будущее

Подтверждённой точности на реальной пекарне пока нет. На демонстрационной синтетике ML хуже B1: MAE 0,767225 против 0,416667 на одинаковых 60 парах. Новый протокол для даты t строит признаки только по доступным фактам до t−2. При временной проверке обучение и преобразования отделены от holdout; B1 и ML оцениваются на одинаковых пригодных парах «дата × товар». Показываем MAE, N, покрытие и причины исключений. В пилоте дополнительно будем сохранять прогноз и доступный на момент расчёта снимок до наступления результата. Одного позднее полученного CSV недостаточно, чтобы доказать своевременную доступность данных.

### 5. Сколько денег сэкономит пекарня

Сейчас такой цифры нет. Из ошибки прогноза нельзя напрямую вывести экономию. Сначала нужно проверить качество учёта и пригодность плана, затем согласовать с владельцем способ измерения списаний, дефицита и времени планирования. Простое сравнение «до и после» может зависеть от сезонности и других изменений. Причинный эффект и денежную оценку нельзя приписывать нашему демонстрационному тесту.

### 6. Почему всего пять изделий и можно ли поменять партии

Это намеренно ограниченный MVP, чтобы пройти полный проверяемый цикл. Каталог, партии и пределы зафиксированы на сервере. В интерфейсе можно изменить подтверждаемый выпуск в допустимых границах; менять партии и лимиты через UI пока нельзя. Нельзя переименовать любые пять товаров в наши ID ради импорта. Сначала проверяем соответствие ассортимента пилотной пекарни. Если его нет, понадобится отдельное согласованное изменение каталога. Общей оптимизации загрузки печи пока нет.

### 7. Можно ли открыть сервис всем и безопасны ли данные

Сейчас это локальное приложение или подготовленная конфигурация закрытой демонстрации с общей базой. В приложении нет аккаунтов, ролей и изоляции пекарен. bakery_id связывает модель с данными, но не защищает доступ. Подготовлены внешний Basic Auth, хранение SQLite и проверяемое резервное восстановление; контейнерный сценарий проверен в Linux CI на указанном в VERIFICATION.md commit. Это не подтверждает работу на выбранном хостинге или ноутбуке пользователя. Публичное размещение требует отдельной настройки и проверки; реальные данные не выкладываем в Git и открытое демо.

### 8. Что конкретно нужно от первой пекарни и как понять, что пилот удался

Нужны разрешение на использование, подходящий ассортимент и ежедневные агрегаты в физических штуках: остатки, выпуск, продажи, списания, прочее выбытие, календарь и сведения о дефиците. Важно знать, когда каждый итог был готов. До наблюдения будущих результатов согласуем период, горизонт, исключения и критерий полезности. Сначала работаем в наблюдательном режиме: записываем прогнозы, а выпуск определяет владелец. Итогом станет воспроизводимое сравнение B1/ML с покрытием и разбором пригодности плана, даже если улучшения не будет.

## Порядок записи резервного видео

### До включения записи

1. Диас фиксирует проверенный SHA и фактическую среду. Выполняет локальный checklist и ручную QA; результат CI их не заменяет.
2. Использовать отдельную демонстрационную SQLite и только `synthetic_demo.csv`. Закрыть окна с паролями, реальными файлами, личными сообщениями и уведомлениями.
3. Проверить масштаб интерфейса, читаемость чисел и запись звука. Отключение интернета не требуется: важнее заранее убедиться, что локальный показ запускается без внешних сервисов.
4. Подготовить модель для target `2026-10-13`, cutoff `2026-10-11`. При записи 14 октября UTC+5 или позднее назвать это историческим воспроизведением. Не переносить cutoff на незавершённый день ради красивого результата.
5. Проверить для каждого товара фактический метод, готовность, допустимость партии 84 для p1, сохранение, экспорт, reload и restart. Если ML недоступен, записать честный резервный путь B1 с причиной.

### Основной дубль около 90 секунд

Следуйте таблице «Сценарий» выше и тексту речи. Обучение заранее назовите подготовленным, даты 13/11 октября — историческим воспроизведением. Начните с синтетического импорта, затем покажите метод, план 84 для p1, подтверждение, историю, экспорт и ограничения. Не показывайте ожидание как мгновенное обучение.

### Короткие дополнительные доказательные фрагменты

Записать отдельно и сохранить как резерв, не обещая включить их в конкурсный ролик до подтверждения регламента:

- Невалидный баланс: импорт `invalid_balance.csv` отклонён целиком, ранее сохранённые данные остались.
- Сохранность: записать ID плана и версии, перезапустить API с той же SQLite, открыть тот же план и сравнить экспорт. Перезагрузка страницы не заменяет рестарт процесса.
- Fallback: явно показать B1/manual и причину, если такой сценарий подготовлен; не подменять его подписью ML.

После записи полностью воспроизвести локальный файл, проверить звук, читаемость, начало/конец и отсутствие секретов. Сохранить копию на согласованном носителе; чужим сервисам запись пока не отправлять. Название файла может содержать дату и короткий SHA. Не заявлять, что видео уже записано, пока существует только этот сценарий.
