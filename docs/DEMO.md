# Демонстрация примерно за 90 секунд

## Речь для синтетического сценария Cloud Game Zone (около 90 секунд)

«BakePlan помогает решить два похожих вопроса: сколько приготовить в пекарне и сколько готового товара заказать для бара компьютерного клуба. Для Cloud Game Zone мы подготовили **полностью синтетический** пример из шести товаров за 91 день. Он показывает возможный рабочий процесс; это не кассовая история клуба.

Выбираю режим закупки и загружаю CSV вместе с каталогом поставщика. Приложение проверяет баланс каждого дня и сохраняет источник. На пятницу 16 октября делаю исторический прогноз по данным только до 14 октября. Модель Ridge использует общий расчёт, но для каждого товара проходит отдельную внутреннюю проверку против простого прогноза по похожим дням. Здесь ML используется для колы, холодного чая и энергетика. Для воды, чипсов и шоколада проверка не дала преимущества, поэтому остаётся простой метод.

Прогноз продаж ещё не заказ. Я задаю доступный остаток и срок поставки, вижу предложение в целых упаковках: например, вода — 24 штуки, две упаковки по 12. Владелец может изменить решение: ставлю 36, подтверждаю и нахожу эту версию в истории и CSV экспорте.

Реальные упаковки, цены, дефициты и время владельца ещё нужно подтвердить в интервью и пилоте. Этот показ доказывает работу процесса и безопасных запасных методов, но не точность на будущих продажах клуба и не денежную экономию».

Только синтетические данные `fixtures/synthetic_demo.csv`, созданные для проекта: пять изделий, 56 календарных дней, никаких исходников реальной пекарни. Не называть этот файл реальными продажами и не показывать синтетический MAE как точность продукта.

## Подготовка до записи

Стартовый экран — «План». Разделы «Данные» и «История» доступны в основной навигации; необязательная подготовка модели находится в «Дополнительно → Качество прогноза». Заголовок показывает выбранную дату, а не всегда «завтра»; прошедшая/текущая дата помечена историческим воспроизведением. Без выбранного набора старт предлагает одно главное действие «Перейти к данным». Способ «По похожим дням недели» остаётся выбранным по умолчанию; обучение экспериментальной модели необязательно.

- Чистый запуск по README, отдельная демонстрационная SQLite. Убедиться в `/api/health` и записать commit.
- Открыть «Данные» → «Загрузить демо CSV», импортировать с source `synthetic`, bakery `demo`, происхождением «Синтетическая демонстрация BakePlan».
- Для согласованного двухдневного горизонта: дата плана/прогноза `2026-10-13`, срез `2026-10-11`. Для сегодняшней записи после 13 октября это явно историческое воспроизведение.
- Обучить модель заранее: дождаться статуса и проверить каждый товар. Если модель не готова, показать честный B1 и причину, не менять подпись на ML.
- Рассчитать план, проверить допустимые партии. Заранее проверить экспорт, перезагрузку и рестарт на той же БД. Не выдавать этот чек-лист за выполненную ручную QA.


## Отдельная чистая база для репетиции

«Начать заново» здесь означает выбрать новый путь, а не удалить прежнюю SQLite. Сначала остановите API через Ctrl+C и запишите его прежний `BAKEPLAN_DB`. Команды выполняются из корня проверенного checkout с уже установленными зависимостями. Старые `.sqlite3`, `-wal`, `-shm` и резервные копии не трогаем. В интерфейсе после запуска обновите страницу и выберите новый импорт; не используйте сохранённые ID предыдущей базы.

Windows PowerShell, нативный запасной запуск:

```powershell
$demoDir = Join-Path (Join-Path (Get-Location) "data") ("defense-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $demoDir -ErrorAction Stop | Out-Null
$env:BAKEPLAN_DB = Join-Path $demoDir "demo.sqlite3"
Write-Host "Новая демонстрационная БД: $env:BAKEPLAN_DB"
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Linux, нативный запуск:

```sh
mkdir -p data
demo_dir=$(mktemp -d "$PWD/data/defense-XXXXXXXX") || exit 1
export BAKEPLAN_DB="$demo_dir/demo.sqlite3"
printf 'Новая демонстрационная БД: %s\n' "$BAKEPLAN_DB"
.venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Frontend запускается отдельно по [README](../README.md#быстрый-запуск). Для повторного открытия этого же дубля используйте **напечатанный путь**, а не выполняйте генерацию нового каталога. Для рестарта проверки также оставьте тот же путь. Для возврата к рабочей базе остановите demo API и восстановите ранее записанный `BAKEPLAN_DB`. Не меняйте путь у работающего сервера и не копируйте живую БД.

Для Docker используйте [LOCAL_WINDOWS](LOCAL_WINDOWS.md) и его отдельный project/volume. Приведённые выше команды относятся только к нативному процессу; они не переключают БД контейнера. Не применяйте `down --volumes`, factory reset или volume prune ради чистого дубля. Если Docker-демо уже содержит важные данные, сначала сохраните и проверьте backup по инструкции; до отдельного выбора нового имени БД используйте нативную чистую демонстрацию.

## Ожидаемый результат на синтетическом примере

Текущие контрольные числа v3 воспроизводятся через [replay_demo.py](../scripts/replay_demo.py) и проверяются [регрессионным тестом](../backend/tests/test_demo_replay.py). Старый replay на HEAD `9948d911b5211e3a439c64733f61d82d4f405d49` не подтверждает числа v3. Проверка текущего рабочего дерева прошла; для итогового commit повторить replay и сохранить его отчёт с SHA, dirty status и хешами исходников. Это FastAPI TestClient и закрытие/повторное открытие приложения **в одном процессе**; браузерный показ и настоящий OS/process restart этим запуском не подтверждаются.

Вход: 280 строк, пять товаров, 56 дат `2026-08-17`…`2026-10-11`; канонический SHA-256 содержимого `fixtures/synthetic_demo.csv` с окончаниями строк LF (Git blob): `3811e52ebd6b3bebebafc8b4c479446e8cf263cdd9d056303394778f00d985ce`. Обучение и прогноз со срезом `2026-10-11`, целевая дата `2026-10-13`, режим исторического воспроизведения. Все пять товаров технически готовы, фактический метод после обучения — ML.

| Товар | B1, шт. | ML, шт. | Рекомендация | Подтверждение в дубле |
|---|---:|---:|---:|---:|
| p1, хлеб пшеничный | 26 | 27,644833 | 24 | 84 |
| p2, хлеб ржаной | 30 | 30,984142 | 30 | 30 |
| p3, багет | 34 | 34,930850 | 32 | 32 |
| p4, круассан | 38 | 38,877558 | 36 | 36 |
| p5, булочка | 42 | 42,824266 | 48 | 48 |

Таблица округлена до шести знаков. Точное значение API для p1 — `27.644832659891915`; интерфейс прогноза и плана показывает `27.6` через `toFixed(1)` ([ForecastResult](../frontend/src/ForecastResult.tsx), [PlanningSection](../frontend/src/PlanningSection.tsx)). При checkout на Windows окончания CRLF могут изменить хеш сырых байтов CSV; отчёт хранит raw и canonical-LF SHA-256, между платформами сверяйте `fixture.canonical_lf_sha256`. B1 использует `2026-10-06`, `2026-09-29`, `2026-09-22`, `2026-09-15`. **84 для p1 выбрано только для демонстрации ручного изменения; это не прогноз и не обоснованная рекомендация выпуска.** У p5 B1 = 42 равноудалено от допустимых 36 и 48 (правило выбирает меньшее), но ML-прогноз 42,82 ближе к 48. **Числа относятся к protocol v3 основной ветки. Для записи выбирайте артефакт того же SHA из [проверенного CI](../VERIFICATION.md); более старый дубль v2 не подтверждает числа v3.**

Дополнительные ожидания:

- До обучения в отдельной чистой базе запрос ML явно возвращает B1 с причиной отсутствия модели.
- `invalid_balance.csv`: HTTP 422, `INVALID_CSV`, нарушение баланса во второй строке; импорт отклонён целиком, количества записей в таблицах не меняются.
- После подтверждения: пять строк CSV, сохранены отдельные forecast/recommended/confirmed; две записи редакций, текущая revision=1. Повтор прежнего запроса подтверждения не создаёт ещё одну редакцию.
- После закрытия/открытия app lifespan на той же SQLite replay сохранил точные данные, модель, прогноз, план и байты CSV. Для утверждения о рестарте API на ноутбуке отдельно выполнить настоящий restart из checklist.
- На встроенном holdout этого примера **ML хуже B1**: MAE 1,058562 против 0,416667, общих пар 60, покрытие 60/60. Это контроль воспроизведения на вымышленных данных, не оценка качества на пекарне. Подробности и отличие от forward-window CLI — в [EVALUATION](EVALUATION.md#контрольные-числа-встроенной-оценки-на-синтетике).

## Точная последовательность ручной репетиции

Это checklist для выполнения на целевом компьютере, а не заявление о уже пройденной ручной QA. Основной сценарий всегда использует цель `2026-10-13` и срез `2026-10-11` (t−2). Старый пример B1=65 и рекомендации 60 на `2026-10-12` относится к другой контрольной точке и в этот показ не включается.

1. Запустите отдельную чистую demo SQLite по инструкции выше. Откройте «Данные» и нажмите «Загрузить демо CSV», проверьте источник `synthetic`, пекарню `demo` в «Параметры набора» и физические штуки; для совпадения с replay замените автозаполненное происхождение на «Синтетическая демонстрация BakePlan», затем «Проверить и импортировать». Ожидается 280 строк и период 17.08.2026–11.10.2026. Выбор файла означает только подготовку: до нажатия «Проверить и импортировать» новые данные не сохранены. Памятка «Какие данные нужны?» объясняет состав истории и фиксированный каталог. Исходный CSV скрыт в «Вставить или проверить CSV»; сохранённый источник и период остаются видны. Переключение разделов сохраняет черновик в этой вкладке. При перезагрузке восстанавливаются только серверные значения, не несохранённый ввод; браузер предупреждает о ручных правках. Другой набор можно открыть через «Продолжить работу с сохранённым набором» без повторного импорта. На телефоне изделия отображаются карточками без горизонтальной прокрутки; прогноз, рекомендация, ваш выпуск, сохранённое значение, шаг партии и предел остаются отдельными.
2. **До обучения** через «Дополнительно → Качество прогноза» задайте срез `2026-10-11`, дату `2026-10-13`, «Способ прогноза» = «Экспериментальный расчёт». Нажмите «Получить прогноз». Ожидайте фактический B1 и причину отсутствия модели; для p1 отображается `26.0`. Запишите этот отдельный резервный фрагмент сейчас.
3. Нажмите «Подготовить экспериментальный расчёт» с тем же срезом, дождитесь ready и проверьте все пять товаров. Снова нажмите «Получить прогноз»: фактический метод ML, p1 отображается `27.6`. Интерфейс сообщает, что экспериментальный расчёт оказался менее точным. Точные MAE `0,416667` для B1 и `1,058562` для ML, парное N=60 и покрытие 60/60 сверяются в API/replay и [EVALUATION](EVALUATION.md). Чем меньше MAE, тем лучше; техническая готовность здесь не означает победу над B1.
4. Откройте «План» и отдельно проверьте дату `2026-10-13`, срез `2026-10-11`, открытый целевой день и «Способ расчёта» = «Экспериментальный расчёт». Нажмите «Рассчитать план». Для p1 прогноз `27.6`, рекомендация 24; остальные рекомендации 30/32/36/48.
5. В «Количество Хлеб пшеничный» замените 24 на 84. Остальные количества оставьте без изменений. Нажмите «Подтвердить и сохранить». Проверьте «Сохранено: 84 шт.», статус «Подтверждён» и версию 1. ID плана проверяется в ответе API, а не в основном интерфейсе. Это пример ручного управления, не совет выпекать 84 штуки.
6. Обновите страницу: выбранный сохранённый набор и последний открытый план восстанавливаются с сервера. Откройте «История» (список загружается автоматически) → «Открыть план» у нужной даты и экспортируйте CSV. Источник и статус подписаны по-русски, Технические идентификаторы сверяются через API или экспорт. Проверьте пять строк, target/cutoff, метод ML, p1 forecast=`27.644832659891915`, recommended=24, confirmed=84. Отдельно выполните настоящий перезапуск API с тем же путём SQLite и повторите чтение, если собираетесь утверждать сохранность после рестарта на этом компьютере.
7. **После сохранения плана** откройте «Данные», загрузите `fixtures/invalid_balance.csv` и нажмите «Проверить и импортировать». Ожидается понятный отказ из-за баланса (API 422/INVALID_CSV). Вернитесь в историю: тот же ID плана, подтверждённые 84 и экспорт должны сохраниться. Это проверка отсутствия потери уже сохранённого состояния; не очищайте базу между шагами 5–7.

Для основного 90-секундного дубля модель уже подготовлена; fallback и ошибочный импорт снимаются дополнительными фрагментами. Полный прогон со временем обучения не обязан укладываться в 90 секунд.

## Текст шести слайдов

### Слайд 1. Как пекарне подготовить выпуск на завтра

BakePlan помогает владельцу небольшой пекарни составить план по пяти изделиям.

- История продаж и товарный баланс в одном CSV.
- Прогноз и рекомендация с учётом партии и предела выпуска.
- Владелец проверяет, корректирует и подтверждает план.

Цель пилота: проверить, помогает ли такой процесс планировать выпечку. Сокращение списаний и денежная экономия пока не доказаны.

### Слайд 2. Что уже работает

CSV → проверка → обучение при достаточной истории → прогноз → допустимый план → ручное подтверждение → история и экспорт.

- Ошибочный баланс или дубликат отклоняет весь импорт.
- Прогноз, рекомендация и подтверждённый выпуск хранятся отдельно.
- Данные, модели и планы сохраняются в SQLite.

На показе используются вымышленные данные: пять изделий, 56 календарных дней.

### Слайд 3. Как устроен прогноз

- B1: средние продажи в последние четыре подходящих одноимённых дня недели, найденные в пределах 56 дней.
- ML: B1 с относительной поправкой общей Ridge-модели, фиксированное α = 200. Производственное демо не отбирает ML по преимуществу над B1; [правило закупочного отбора и fallback](EVALUATION.md#фактические-параметры-отбор-и-fallback) описано отдельно.
- Признаки: доступная история продаж, лаги, скользящие средние, день недели.
- Нет пригодной ML-модели: явно показываем B1; нет подходящей истории: нужен ручной план.

Для цели t используем завершённые факты только до t−2. Это допущение о готовности учёта нужно подтвердить с пекарней.

### Слайд 4. Решение остаётся у владельца

- Пять фиксированных изделий, размер партии и дневной предел каждого.
- Закрытый день: выпуск 0.
- Перенос остатков или частый дефицит/неизвестное наличие отключают автоматическую рекомендацию.
- Общую загрузку печи и итоговые количества проверяет человек.

Пример: пшеничный хлеб, партия 12, предел 100 штук. Наибольший допустимый выпуск — 96; ручной вариант 84 допустим.

### Слайд 5. Что подтверждено и что предстоит проверить

Подтверждаем работу программы на синтетических сценариях и автоматизированных проверках. Состояние CI проверяем по точному SHA.

Для сравнения B1 и ML используем одинаковые пары «дата × товар» и одинаковый горизонт. Показываем MAE, число пар, покрытие и исключения. На синтетическом примере MAE модели выше, чем у B1; преимущества ML здесь нет.

Реальная точность, неудовлетворённый спрос, снижение списаний и экономия пока не измерены. Следующий шаг — разрешённые данные одной пекарни и заранее зафиксированный будущий период проверки.

### Слайд 6. Команда и следующий шаг

- Нурлан: модель, Python API и хранение.
- Бага: интерфейс.
- Диас: независимая проверка и воспроизведение.
- Асыл: источник данных, разрешения и границы пилота.

Ближайшие действия: ручная проверка на целевом ноутбуке, резервная видеозапись и согласование данных пилота.

Текущий MVP: одна пекарня, пять изделий, локальный доверенный запуск. Публичный хостинг, аккаунты и изоляция пользователей не готовы.

Примечание для докладчика: стартовый код создан с помощью Codex. Это раскрыто в CONTRIBUTING.md. Требования конкурса к AI-инструментам и составу сдачи ещё нужно подтвердить у организатора; не утверждать, что допуск уже получен.

## Речь примерно на 90 секунд

Текст содержит 186 слов; длительность проверить вслух. Экранные действия репетировать отдельно, затем совместить с речью. Не ускорять речь ради показа ожидания обучения: модель подготовить заранее и прямо это назвать.

«BakePlan помогает небольшой пекарне подготовить выпуск на завтра. В нашем MVP пять изделий, а окончательное решение принимает владелец.

На экране вымышленные данные за восемь недель. Загружаем CSV: программа проверяет формат, дубликаты и товарный баланс. Пропущенный день не превращается в нулевые продажи.

Для этого набора модель уже обучена. Простой ориентир B1 усредняет продажи в последние подходящие одноимённые дни недели. Наша экспериментальная модель добавляет к нему поправку Ridge. Она использует только доступную историю. Если модель не готова, интерфейс показывает B1 и причину перехода.

Сейчас воспроизводим план на тринадцатое октября по фактам до одиннадцатого. Такой срез соответствует сценарию, когда вчерашний учёт уже завершён, а сегодняшний ещё нет.

Далее учитываем партии и предел выпуска. Для пшеничного хлеба выбираем восемьдесят четыре штуки, подтверждаем план, открываем историю и экспортируем CSV. Прогноз, рекомендация и подтверждённое количество сохраняются отдельно. Общую загрузку печи проверяет человек.

В оценке сравниваем B1 и ML на одинаковых датах и показываем число наблюдений и покрытие. На этом синтетическом примере ML хуже B1.

Эта демонстрация подтверждает работу программы. Реальную точность и влияние на списания предстоит проверить с пекарней. Следующий шаг — разрешённая история и будущий период проверки по заранее согласованным правилам».

## Восемь сложных вопросов жюри

### 1. Где здесь AI и зачем он, если есть простое среднее

Встроена обучаемая Ridge-регрессия, которая корректирует B1 по признакам истории. B1 остаётся прозрачной точкой сравнения и резервным методом. На текущем синтетическом holdout ML даже хуже B1: MAE 1,058562 против 0,416667 на 60 общих парах; у четырёх из пяти товаров этого набора продажи по дням недели постоянны, так что сравнение держится на 12 днях p1. Эти числа проверяют воспроизведение, не качество на реальной пекарне. Преимущество нужно проверять на одинаковом будущем периоде. Если ML хуже или часто недоступен, это будет результатом проверки, а не поводом скрыть B1. Соответствие конкурсной категории AI подтверждается правилами организатора, ответа пока нет.

### 2. На каких данных обучались и откуда они

В демонстрации используем созданную для проекта синтетику: пять изделий и 56 дней. Она позволяет проверить импорт, обучение, fallback и сохранение, но не доказывает точность для пекарни. Ранее команда исследовала внешний sales-only набор BreadBasket. Его товарные строки не равны физическим штукам; старый просмотренный test и улучшение 3,35% не являются метрикой нынешней интегрированной модели. Для пилота нужны разрешённые агрегаты конкретной пекарни с понятными единицами и балансом.

### 3. Если хлеб закончился, продажи ведь ниже спроса. Как это учитывается

Да. Модель прогнозирует наблюдаемые продажи и не восстанавливает потерянный спрос. Для физического учёта дни с дефицитом или неизвестным наличием исключаются из обучающих меток. Также исключаются закрытые дни и дни с переносом остатков. Если более половины наблюдаемых открытых дней за используемое окно имеют дефицит или неизвестное наличие, автоматическая рекомендация отключается. Перенос остатков тоже требует ручного плана. Нулевой остаток не считается доказательством отсутствия дефицита.

### 4. Какова точность и как вы исключили заглядывание в будущее

Подтверждённой точности на реальной пекарне пока нет. На демонстрационной синтетике ML хуже B1: MAE 1,058562 против 0,416667 на одинаковых 60 парах (фактически 12 дней p1). Новый протокол для даты t строит признаки только по доступным фактам до t−2. При временной проверке обучение и преобразования отделены от holdout; B1 и ML оцениваются на одинаковых пригодных парах «дата × товар». Показываем MAE, N, покрытие и причины исключений. В пилоте дополнительно будем сохранять прогноз и доступный на момент расчёта снимок до наступления результата. Одного позднее полученного CSV недостаточно, чтобы доказать своевременную доступность данных.

### 5. Сколько денег сэкономит пекарня

Сейчас такой цифры нет. Из ошибки прогноза нельзя напрямую вывести экономию. Сначала нужно проверить качество учёта и пригодность плана, затем согласовать с владельцем способ измерения списаний, дефицита и времени планирования. Простое сравнение «до и после» может зависеть от сезонности и других изменений. Причинный эффект и денежную оценку нельзя приписывать нашему демонстрационному тесту.

### 6. Почему всего пять изделий и можно ли поменять партии

Это намеренно ограниченный MVP, чтобы пройти полный проверяемый цикл. Каталог, партии и пределы зафиксированы на сервере. В интерфейсе можно изменить подтверждаемый выпуск в допустимых границах; менять партии и лимиты через UI пока нельзя. Нельзя переименовать любые пять товаров в наши ID ради импорта. Сначала проверяем соответствие ассортимента пилотной пекарни. Если его нет, понадобится отдельное согласованное изменение каталога. Общей оптимизации загрузки печи пока нет.

### 7. Можно ли открыть сервис всем и безопасны ли данные

Сейчас это локальное приложение или подготовленная конфигурация закрытой демонстрации с общей базой. В приложении нет аккаунтов, ролей и изоляции пекарен. bakery_id связывает модель с данными, но не защищает доступ. Подготовлены внешний Basic Auth, хранение SQLite и проверяемое резервное восстановление; контейнерный сценарий проверен в Linux CI на указанном в VERIFICATION.md commit. Это не подтверждает работу на выбранном хостинге или ноутбуке пользователя. Публичное размещение требует отдельной настройки и проверки; реальные данные не выкладываем в Git и открытое демо.

### 8. Что конкретно нужно от первой пекарни и как понять, что пилот удался

Нужны разрешение на использование, подходящий ассортимент и ежедневные агрегаты в физических штуках: остатки, выпуск, продажи, списания, прочее выбытие, календарь и сведения о дефиците. Важно знать, когда каждый итог был готов. До наблюдения будущих результатов согласуем период, горизонт, исключения и критерий полезности. Сначала работаем в наблюдательном режиме: записываем прогнозы, а выпуск определяет владелец. Итогом станет воспроизводимое сравнение B1/ML с покрытием и разбором пригодности плана, даже если улучшения не будет.

## Порядок записи резервного видео

### До включения записи

1. Диас фиксирует проверенный SHA и фактическую среду. Выполняет локальный checklist и ручную QA; результат CI их не заменяет.
2. Использовать отдельную демонстрационную SQLite и только `synthetic_demo.csv`. Закрыть окна с паролями, реальными файлами, личными сообщениями и уведомлениями.
3. Проверить масштаб интерфейса, читаемость чисел и запись звука. Отключение интернета не требуется: важнее заранее убедиться, что локальный показ запускается без внешних сервисов.
4. Подготовить модель для target `2026-10-13`, cutoff `2026-10-11`. При записи 14 октября UTC+5 или позднее назвать это историческим воспроизведением. Не переносить cutoff на незавершённый день ради красивого результата.
5. Проверить для каждого товара фактический метод, готовность, допустимость партии 84 для p1, сохранение, экспорт, reload и restart. Если ML недоступен, записать честный резервный путь B1 с причиной.

### Основной дубль около 90 секунд

Следуйте таблице «Сценарий» выше и тексту речи. Обучение заранее назовите подготовленным, даты 13/11 октября — историческим воспроизведением. Начните с синтетического импорта, затем покажите метод, план 84 для p1, подтверждение, историю, экспорт и ограничения. Не показывайте ожидание как мгновенное обучение.

### Короткие дополнительные доказательные фрагменты

Записать отдельно и сохранить как резерв, не обещая включить их в конкурсный ролик до подтверждения регламента:

- Невалидный баланс: импорт `invalid_balance.csv` отклонён целиком, ранее сохранённые данные остались.
- Сохранность: записать ID плана и версии, перезапустить API с той же SQLite, открыть тот же план и сравнить экспорт. Перезагрузка страницы не заменяет рестарт процесса.
- Fallback: явно показать B1/manual и причину, если такой сценарий подготовлен; не подменять его подписью ML.

После записи полностью воспроизвести локальный файл, проверить звук, читаемость, начало/конец и отсутствие секретов. Сохранить копию на согласованном носителе; чужим сервисам запись пока не отправлять. Название файла может содержать дату и короткий SHA. Не заявлять, что видео уже записано, пока существует только этот сценарий.

### Воспроизводимая автоматическая запись реального интерфейса

Отдельный сценарий [video/capture.spec.ts](../video/capture.spec.ts) записывает **непрерывное беззвучное видео** настоящего Vite/FastAPI через Playwright `recordVideo`, 1440×1000. Это реальная работа браузера с приложением, а не монтаж скриншотов, анимация макета или запись дикторского текста выше. Автоматический прогон в Windows CI не заменяет ручную QA на целевом ноутбуке. До успешного артефакта с `capture_status: complete` наличие сценария не означает, что запись получена.

Запуск из корня checkout после установки зависимостей по README:

```sh
npx playwright test --config=playwright.video.config.ts
```

В PowerShell при ограничении политики выполнения используйте `npx.cmd`. При уже установленном Chromium можно передать его путь через `BAKEPLAN_CHROMIUM_PATH`; выбранные браузер, версия и ОС попадут в отчёт. Сценарий сам запускает API на `127.0.0.1:18003`, Vite на `127.0.0.1:15175` и создаёт новый уникальный путь SQLite во временном каталоге. Занятые порты дают ошибку, существующие серверы и рабочая база не переиспользуются. SQLite не входит в артефакт. Нужны установленный Playwright Chromium и его штатный видеорекордер; отдельная установка ffmpeg в CI не требуется.

Все действия, меняющие данные, выполняются через настоящие элементы интерфейса: выбор файла `fixtures/synthetic_demo.csv`, импорт, даты 13/11 октября, обучение, прогноз, явный выбор ML в плане, расчёт, 84 для p1 и подтверждение. Ответы API не подменяются, DOM/CSS не изменяются, надписи поверх экрана не создаются. Только синтетический файл с проверенным canonical-LF SHA-256, никаких данных пекарни.

Ориентиры непрерывного дубля:

| Секунды | Фактическое действие |
|---|---|
| 0–20 | Пустой план, выбор синтетического CSV, настоящий импорт и сохранённые 280 строк |
| 20–27 | Дата `2026-10-13`, срез `2026-10-11`, историческое воспроизведение; исходный метод плана B1 |
| 27–47 | Настоящее обучение без предварительной подготовки; готовность и читаемая оценка MAE B1 `0,416667`, ML `1,058562`, N=60, покрытие 60/60, явное «ML хуже B1» |
| 47–58 | Настоящий диагностический ML-прогноз: p1 `27.6` в интерфейсе, `27.644832659891915` в API |
| 58–75 | Явный выбор ML только для демонстрации, рекомендация 24, затем ручные 84; три количества остаются различными |
| 75–91 | Подтверждение версии 1, сохранённая история, нажатие настоящей ссылки экспорта CSV |
| 91–105 | Перезагрузка страницы, повторное открытие того же плана из истории, сохранённые 84 и точное равенство API-состояния |

Сценарий держит сцены по монотонному таймеру с целью 105 секунд, а не складывает произвольные паузы. Реальное ожидание обучения остаётся в записи. Проверяется 100–110 секунд до закрытия страницы и 90–120 секунд по метаданным окончательно записанного WebM. Если медленный запуск не укладывается, тест завершается ошибкой: видео не ускоряется и не выдаётся за готовый дубль. Предварительная подготовка модели из ручного сценария к этому автоматическому дублю **не относится**.

Результат расположен в `test-results/video/**/evidence/` и загружается отдельным CI-артефактом `bakeplan-demo-video-<SHA>-<attempt>`, независимо от 27 PNG до/после и существующих регрессионных сценариев:

- `bakeplan-demo.webm`: настоящая непрерывная запись браузера без звука;
- `manifest.json`: точный source SHA, признак dirty, хеши fixture/видео/CSV, браузер/ОС, реальные времена сцен и обучения, длительность WebM, ответы API для модели/прогноза/черновика/подтверждения и открытого после reload плана;
- `confirmed-plan.csv`: файл, скачанный реальной ссылкой из истории; его байты дополнительно сравнены с экспортом API;
- `DEMO.md`: инструкция именно из записанного checkout.

Перед распространением проверить `capture_status`, соответствие SHA запуска, `source_dirty: false` у окончательного CI-артефакта и наличие всех трёх основных файлов. Не выбирать черновую запись из упавшего прогона. Перезагрузка страницы доказывает чтение сохранённого состояния; этот дубль не является проверкой настоящего OS/process restart.

Для MP4 можно локально перекодировать проверенный WebM доступным ffmpeg, без обрезки, ускорения, дорисовки или добавления неподтверждённой озвучки:

```sh
ffmpeg -i bakeplan-demo.webm -c:v libx264 -preset medium -crf 18 -pix_fmt yuv420p -an -movflags +faststart bakeplan-demo.mp4
ffprobe -v error -show_entries format=duration:stream=codec_name,width,height -of json bakeplan-demo.mp4
```

Отдельно убедиться, что итоговый MP4 имеет 1440×1000 и длительность 90–120 секунд. Полностью просмотреть его и проверить кадры импорта, оценки, трёх разных количеств, сохранения и истории. MAE и лимиты должны читаться при обычном размере. **84 — демонстрация ручного решения, не рекомендация выпуска. ML в этом примере хуже B1; реальная точность и экономия не доказаны.** Если звук не добавлялся, честно назвать ролик беззвучным; наличие текста речи в документе не означает наличие озвучки в MP4.
