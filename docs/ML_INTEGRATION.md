# ML в локальном BakePlan

Экспериментальная модель встроена в путь «импорт → обучение → статус → прогноз». Для истории в физических штуках её прогноз также доступен в черновике плана с прежними ограничениями и ручным подтверждением. Данные, модели, планы и редакции сохраняются в одной локальной SQLite.

Это инженерная интеграция, а не доказательство превосходства ML, восстановленного спроса, экономии или готовности к эксплуатации. Старый финальный тест BreadBasket уже использован в предыдущем исследовании; его нельзя представить новым независимым подтверждением этой модели. Для следующего независимого вывода нужен заранее отделённый, ещё не просмотренный период. Синтетические тесты проверяют поведение программы.

## Перед импортом новой пекарни

Владелец данных вместе с Асылом подтверждает право на использование, происхождение, смысл единиц, ассортимент и момент доступности дневных итогов. Достаточно агрегатов «дата × товар»: персональные данные покупателей и платёжные реквизиты не нужны. Реальные CSV, SQLite, резервные копии и приватные отчёты нельзя добавлять в Git.

Укажите `source` (`synthetic`, `local` или `external`), устойчивый `bakery_id`, `target`, `unit`, `provenance` и `schema_version`. `bakery_id`, `target`, `unit`, `provenance` нужно передавать вместе; источник `synthetic` предназначен только для вымышленных тестовых данных. Идентификатор пекарни: 1–64 латинские буквы, цифры, `_` или `-`.

Есть два несовместимых контракта:

- `history-1` / `sold_units` / `physical_unit`: фактически проданные физические штуки, CSV [history_template.csv](../fixtures/history_template.csv). Укажите реальные `is_open`, `opening`, `produced`, `sold`, `waste`, `closing`, `other_out`, `stockout_status`; баланс `opening + produced = sold + waste + closing + other_out` обязателен. `stockout_status`: `none`, `occurred` или `unknown`. Нулевой остаток сам по себе не означает отсутствие дефицита.
- `sales-1` / `item_line_count` / `item_line`: число товарных строк продаж на дату, CSV [sales_template.csv](../fixtures/sales_template.csv). Это не количество изделий. Остатки, производство, списания, доступность товара и скрытый спрос из строк продаж не выводятся. Каждая строка входного CSV содержит агрегат для одной пары «дата × товар».

Оба шаблона содержат только заголовки. Пустой шаблон импортировать нельзя: заполните его разрешёнными фактическими наблюдениями. UTF-8, запятая, дата `YYYY-MM-DD`, неотрицательные целые, без повторов «дата × товар». Пропущенные даты не превращаются в нули; ноль допустим только как явно известное наблюдение. Ошибка отклоняет импорт целиком.

Для `history-1` каталог фиксирован: `p1` — хлеб пшеничный, `p2` — хлеб ржаной, `p3` — багет, `p4` — круассан, `p5` — булочка. Проверяйте смысл сопоставления, размер партии и предел выпуска; нельзя переименовать чужие товары в p1…p5 ради прохождения импорта. Иной физический ассортимент требует отдельного изменения каталога и проверки. Для sales-only разрешены собственные стабильные строковые ID, максимум 50 товаров; этот путь не создаёт производственный план.

Повтор того же CSV с теми же метаданными, источником и схемой возвращает прежний набор. Иная пекарня даже с одинаковым CSV получает отдельный набор. Исправленный CSV или изменённые метаданные создают новую неизменяемую версию: обучите её отдельно. Модель чужого набора, пекарни или единицы использовать нельзя. Старые импорты без явных метаданных по-прежнему доступны для B0/B1; для обучения импортируйте CSV заново с полной идентичностью.

## Работа в приложении

1. Запустите API и интерфейс по [README](../README.md). Сервер привязывайте к `127.0.0.1`; сохраняйте постоянный путь `BAKEPLAN_DB`.
2. В «Импорт истории» выберите единицу, заполните пекарню и происхождение, загрузите CSV и нажмите «Проверить и импортировать». Сверьте отображаемые цель, единицу и диагностику.
3. В «Модель и диагностический прогноз» задайте срез обучения. Он включителен и должен быть строго раньше сегодняшней даты в Asia/Qyzylorda (UTC+5). Если учёт запаздывает, сдвиньте срез назад. Нажмите «Обучить модель».
4. Проверьте `ready` / `not_ready`, причины по товарам, ID модели, версию данных, срез и временной интервал оценки. `ready` означает техническую готовность хотя бы одного товара; отдельные товары могут остаться неготовыми. Это не сертификат точности.
5. Задайте дату строго после среза, выберите ML или B1 и нажмите «Получить прогноз». Рабочий режим по умолчанию: цель — завтра, срез — вчера, разница две календарные даты. По каждому товару проверьте фактический метод, число наблюдений, совместимость горизонта оценки и причину перехода на B1. Если пригодного B1 тоже нет, отображается отсутствие оценки (`manual`, `forecast_mean=null`).
6. Только для `sold_units` рассчитайте отдельный производственный план методом ML. Проверьте партии, ограничения, перенос, дефицит, календарь и общую загрузку печи. Измените количества при необходимости и явно подтвердите. Прогноз, рекомендация и подтверждённый выпуск остаются разными величинами.
7. После перезапуска откройте «Продолжить работу с сохранённым набором» → «Обновить наборы», загрузите нужный набор и обновите модели. План найдите в «Сохранённая история». CSV-экспорт плана содержит пекарню, цель, единицу, версию данных, ID и протокол модели, фактический метод и причину fallback.

Короткий старый units-демо CSV может дать `not_ready`: он не обещает достаточного числа различных дат. Для воспроизводимой проверки полноценного цикла используйте [инструкцию Диасу](manual-qa.md).

## API

Интерактивные тела запросов доступны на `http://127.0.0.1:8000/docs`.

- `POST /api/datasets`: `csv_text`, `source`, `schema_version`, `bakery_id`, `target`, `unit`, `provenance`. Новый импорт — 201, безопасный повтор — 200.
- `POST /api/datasets/{id}/train`: `{"cutoff":"2026-10-11","idempotency_key":"train-review-1"}`. Новый снимок — 201, повтор — 200. Результат содержит статус, причины, идентичность, срез, хеш снимка, протокол и оценку; численные параметры наружу не выдаются. `not_ready` — сохранённый диагностический результат, не ошибка записи.
- `GET /api/datasets/{id}/models`: версии в порядке убывания среза. Повтор обучения того же набора/среза/протокола возвращает исходный неизменяемый результат, даже с новым ключом. Тот же ключ с другим срезом даёт 409.
- `POST /api/forecasts`: `dataset_id`, `cutoff`, `target_date`, `method` (`ML` или `B1`), необязательный `model_id`. Без ID выбирается последний совместимый снимок не позже среза. Явно выбранная модель из будущего или чужого набора отклоняется с 422. Прогноз не сохраняет производственный план. Ответ и каждый товар содержат `evaluation_applicability`: `applicable`, `reason`, `evaluated_horizon_days`, `requested_horizon_days`. Для другого разрыва цель–срез ML может остаться доступным, но MAE двухдневной проверки неприменима к этому горизонту (`forecast_horizon_mismatch`). При B1, fallback, отсутствии пар или частичной готовности товаров общая совместимость не объявляется.
- `POST /api/plans`: прежний контракт плюс `method="ML"` и необязательный `model_id`. Поддержаны также B0/B1. Только физические штуки; для прошлой даты требуется `mode="replay"`. Подтверждение и экспорт остаются `/api/plans/{id}/confirm` и `/api/plans/{id}/export`.

Ошибки имеют `error: {code, message, details}`. 422 — неверный вход/несовместимость; 404 — отсутствующий объект; 409 — конфликт ключа либо повреждённый сохранённый артефакт; 503 — занятое или не завершённое обучение. После временного сбоя повторяйте тот же запрос с тем же ключом. Ошибка входа, занятость и таймаут не создают частичную модель или запись обучения. При повреждении модели прогноз явно переходит на B1, а статус модели сообщает ошибку. Не редактируйте SQLite для «починки»: остановите сервер и проверьте резервную копию.

## Как устроена модель и проверка

Протокол `pooled-relative-ridge-200-v3-horizon-2-experimental` заранее фиксирует B1 + одну Ridge-регрессию (alpha=200), общую для всех товаров набора. Исходные признаки прежние: B1, календарные лаги 2/7/14/28 дней, средние и число наблюдений в календарных окнах 7/28 дней, день недели. Модель видит уровни только относительно B1 своего товара: `(признак − B1) / max(B1, 1)`; цель — `(факт − B1) / max(B1, 1)`. Поэтому товары разного масштаба обучают одну модель, а модель не запоминает абсолютный уровень продаж обучающего периода. Прогноз: `B1 + поправка × max(B1, 1)`, поправка ограничена диапазоном −0,8…+2,0. Модель старше 14 дней относительно среза прогноза продолжает считать, но её holdout-метрики помечаются неприменимыми (`model_too_old`). Протокол v2 обучал отдельную модель на товар по абсолютным признакам и после резкой смены спроса тянул прогноз к старому уровню; на сгенерированных сценариях с падением спроса на 30% его ошибка была на 43% выше B1. Дизайн v3 выбран на сгенерированных данных (отбор на одних seed, проверка на других), не на истории пекарни; это не доказательство точности. В каждом окне доступны только факты до среза включительно. Пропуски признаков заполняются обученной медианой и получают отдельные индикаторы; отсутствующие продажи не становятся нулевыми метками. Лаг 1 заменён лагом 2, потому что в рабочем режиме итог предыдущего целевой дате дня ещё недоступен.

Обучение, holdout и стандартный рабочий прогноз используют один горизонт: для целевой даты t доступны факты только до t−2 включительно (`horizon_days=2`, `feature_cutoff_policy=target_minus_horizon_calendar_days`). Это соответствует значениям UI «завтра / вчера» и сохраняет требование завершённых дней. Другие целевые даты разрешены, но имеют явную проверку совместимости; менять cutoff на незавершённый день ради совпадения с метрикой нельзя.

Единый для товаров хронологический holdout — последние max(7, округлённые вверх 20%) различных наблюдаемых дат. Оценочная модель и преобразования обучаются только по меткам, доступным к первому срезу выдачи прогноза: `first_holdout_cutoff = holdout_start − 2 календарных дня`. Дата непосредственно перед первым holdout не может попасть в fit; такие наблюдаемые даты перечислены в `embargoed_dates`. До этого среза нужно минимум 28 различных наблюдаемых дат и 14 пригодных обучающих строк с признаками для товара (общая модель обучается на строках всех товаров, но товар без собственной истории не получает статус ready); нужен хотя бы один сопоставимый holdout-прогноз. Для непрерывной ежедневной истории минимальная техническая граница теперь 37 дат, а не 35; это следствие среза и округления 20%, не обещание достаточного качества.

Преобразования и оценочная модель заморожены на всём holdout. Более ранние факты holdout можно использовать только после их включения в срез t−2. Это rolling-прогноз с двухдневным отступом: история пополняется, модель не переобучается. Это не проверка длинного прогноза без новых наблюдений. `fit_end` — последняя общая наблюдаемая дата разрешённого обучающего префикса; она не позже `first_holdout_cutoff`. После оценки отдельная рабочая модель переобучается по пригодным меткам до среза обучения включительно, используя для каждой обучающей цели тот же t−2. Её параметры отличаются от замороженной оценочной модели.

B1 и ML сравниваются строго на одних фактически наблюдаемых парах «дата × товар», для которых пригодна метка и получен конечный ML-прогноз. Отсутствующие даты, исключённые метки и B1-fallback не выдаются за успешные ML-наблюдения. По каждому товару `paired_dates` раскрывает точный общий набор дат, `paired_n` — число пар, `paired_start` / `paired_end` — его границы. В общей оценке `paired_dates` — объединение дат, `paired_date_count` — число различных дат, а `paired_n` считает пары по всем товарам; эти числа могут отличаться. Общие MAE взвешены количеством пар, не числом товаров.

`coverage = paired_n / coverage_denominator_n`; знаменатель `eligible_observed_holdout_labels` означает все пригодные наблюдаемые метки holdout, включая те, для которых ML не удалось получить. Он не включает отсутствующие календарные даты и исключённые метки. Общие `holdout_rows`, `holdout_excluded_labels`, `holdout_label_exclusions` отдельно показывают наблюдаемые строки и исключения меток; `exclusions` объясняет неполное покрытие признаками/моделью. По товарам доступны такой же знаменатель и счётчики. Если сопоставимых пар нет, обе MAE равны null, покрытие — 0. Никакого автоматического выбора модели по этим ошибкам нет.

`evaluation_applicability.applicable=true` означает только соответствие протокола, горизонта и наличия пар для ML-диагностики. Это не обещание будущей точности, не оценка рекомендации выпечки и не доказательство экономии. При частичной готовности товаров общий ответ сообщает `partial_product_coverage`; смотреть нужно также отдельные товары. В плане применимость относится к диагностическому прогнозу: ручные ограничения производства продолжают действовать. Закрытый целевой день, отсутствие прогноза товара и каталожная фильтрация B1 не наследуют применимость ML-оценки.

Старые артефакты v1 не изменяются и не интерпретируются как v2: неподдерживаемый протокол явно переходит на B1/manual; повторное обучение создаёт новую версию. Прежний статус `ready` в сохранённом v1 не означает совместимость с новым кодом. Исторические 3,35% из прежнего финального теста BreadBasket относятся только к тому исследованию. Для нового вывода нужен заранее отделённый, ещё не просмотренный период и разрешённые данные конкретной пекарни: записывайте прогнозы до факта на реальном горизонте и с фактической задержкой учёта, затем сравнивайте B1 и ML на одинаковых наблюдениях. Решения о выпуске в пилоте проверяет человек.

Для `sold_units` из обучающих меток исключены закрытые дни, `occurred`/`unknown`, неизвестный или ненулевой перенос остатков. Для sales-only таких полей нет; качество наблюдений и доступность товара неизвестны. В обоих случаях предсказываются наблюдаемые продажи, не неудовлетворённый спрос.

## Ограничения и безопасный запуск

- Максимум 10 000 входных строк; sales-only — до 50 товаров. Импорт принимает каждое количество до 1 000 000 000 включительно; больший вход отклоняется. ML допускает метки/признаки до 1 000 000: неподходящие строки исключаются, а слишком большой ML-прогноз приводит к явному B1-fallback. Диагностический B1 сохраняет принятые наблюдения до 1 000 000 000 без обрезания до ML-предела. Границы доступны в `model.bounds`. Это технические пределы, не допустимый выпуск: партии и максимумы проверяются отдельно.
- Один дочерний процесс обучения одновременно на один процесс API, таймаут 60 секунд; вычислительные библиотеки ограничены одним потоком. Запускайте один процесс Uvicorn без `--workers`: глобальной очереди и координации между серверами нет.
- Модель сохраняется как численный JSON в SQLite с SHA-256-проверкой целостности, без pickle/joblib и без загрузки исполняемых артефактов. Хеш не является защитой от злоумышленника с доступом к диску. Перед обновлением сделайте резервную копию остановленной БД; миграция существующей базы до v3 создаёт `.pre-v3.bak`.
- Нет модели, повреждённый артефакт или неподдерживаемый протокол, недостаточные признаки или неготовый товар означают явный fallback на B1, а при отсутствии истории — `manual`. `requested_method=ML` не гарантирует, что каждый товар рассчитан ML.
- ML не обходит ручные ограничения: закрытый целевой день требует выпуска 0; перенос остатков или более 50% наблюдаемых открытых дней с дефицитом/unknown за 56 дней отключают автоматическую рекомендацию. Диагностическое число может оставаться видимым.
- `bakery_id` обеспечивает смысловую совместимость модели и данных, но не разделение прав доступа. Авторизации, защищённого многопользовательского режима и границ арендаторов нет. Только локальный доверенный запуск; публикация сервера требует отдельного проектирования защиты.
