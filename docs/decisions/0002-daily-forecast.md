# RFC и решение о ежедневном прогнозе

## Предложение

Администратор может запросить первый прогноз кнопкой. По расписанию BakePlan рассчитывает прогноз для нового снимка кассы. Для одной даты и одного снимка результат обоих путей должен совпасть. В версии `f0cf5a4` планировщик импортировал расчёт из модуля веб-запросов, импорт кассы тоже находился рядом с HTTP-маршрутами. При автоматическом прогнозе код дважды читал весь снимок из SQLite.

Рассмотрены три варианта.

| Вариант | Последствие |
|---|---|
| Оставить расчёт в веб-модуле | Планировщик зависит от регистрации HTTP-маршрутов. Изменения интерфейса запроса могут затронуть фоновую работу |
| Вынести расчёт и импорт в обычные модули Python | Оба входа вызывают один расчёт. Уже загруженный снимок можно передать дальше. Ответ API, хранилище и запуск приложения остаются совместимыми |
| Запустить отдельный сервис прогнозов | Можно независимо выделять ресурсы, но появятся сетевой вызов, повторная доставка задания и отдельное развёртывание. Для текущей проблемы этих затрат не требуется |

На одних входах сравниваются количество по каждому товару, даты, метод, предупреждения и идентификатор снимка. Задержка кассы должна сохранить последнюю успешную публикацию. При расчёте по кнопке достаточно одного чтения снимка, при расчёте сразу после импорта достаточно передать уже загруженные данные. Правило Import Linter должно обнаружить прежнюю связь и пропустить исправленный код. [Карта событий и критерии нагрузочной проверки](../architecture/daily-order.md)

## Решение и пересмотр

Выбран общий расчёт внутри существующего сервера. HTTP-обработчик отвечает за запрос и ответ. Планировщик управляет сроками, повторными попытками и записью результата. Расчёт определяет срез и целевую дату, получает значения для товаров и возвращает результат для обоих вызывающих путей. Общий импорт нормализует данные конкретного филиала. Правила направления зависимостей проверяются в GitHub Actions. Модель хранения заказа и правило выбора Chronos-2/B1 сохраняются.

Вопрос об отдельном процессе стоит открыть снова, если на повторяемой нагрузке согласованная цель чтения заказов нарушается, а трассировка показывает конкуренцию с расчётом за ресурсы. Для оценки понадобятся длительность расчёта по филиалам, p95 чтения заказа во время обновления и доля расчётов к сроку. ## Результат проверки

На одном стенде Windows с локальными весами Chronos-2 сравнили с `f0cf5a4` полные ответы для двух товаров из тестовых касс Poster и МойСклад. По каждому провайдеру совпали идентификатор и версия снимка, даты, метод, предупреждения и значения обоих прогнозов. После имитации задержки в обоих случаях сохранился последний успешный результат. Документ OpenAPI совпал для всех 26 путей.

| Измерение | До | После |
|---|---:|---:|
| Полные чтения снимка из SQLite во время расчёта по кнопке | 2 | 1 |
| Полные чтения снимка во время расчёта сразу после импорта кассы | 2 | 0 |

Наблюдаемый выигрыш — устранение повторного чтения снимка. На трёх запусках нагрузочного теста новая версия уложилась в установленный предел, однако разброс времени не позволяет приписать рефакторингу ускорение открытия заказа.
