# Независимая проверка ML: Диас

Это чек-лист, а не утверждение, что ручная проверка уже выполнена. Запишите дату, ОС, версии Python/Node, commit, команды и фактический результат. Используйте отдельную локальную SQLite, например `private/ml-qa.sqlite3`, и синтетические данные. Не запускайте проверки повреждения на рабочей базе.

## Подготовка

1. Установите зависимости и запустите API на `127.0.0.1:8000` одним процессом, интерфейс — на `127.0.0.1:5173`, по [руководству разработчика](DEVELOPMENT.md).
2. Создайте 90 дней исключительно синтетической units-истории p1…p5 до 2026-10-11. Из корня checkout (Python и pytest уже установлены):

   ```sh
   .venv/bin/python -c "from pathlib import Path; from backend.tests.test_ml_api import synthetic_csv; p=Path('private/ml-qa-history.csv'); p.parent.mkdir(parents=True, exist_ok=True); p.write_text(synthetic_csv(), encoding='utf-8')"
   ```

   В PowerShell замените `.venv/bin/python` на `.\.venv\Scripts\python.exe`. Генератор пишет вымышленные тестовые строки; это не шаблон реальной пекарни. Header-only шаблоны для фактических данных: [history](../fixtures/history_template.csv), [sales-only](../fixtures/sales_template.csv).

## Полный цикл новой пекарни

- Импортируйте файл: источник `synthetic`, ID `dias-qa-a`, цель `sold_units`, происхождение «Синтетическая независимая QA». Должны отображаться `physical_unit`, `history-1` и новый ID набора.
- Задайте срез `2026-10-11`, дату прогноза `2026-10-13`. До обучения запросите ML: фактический метод B1 и явная причина отсутствия модели.
- Нажмите «Обучить модель». Должен появиться сохранённый `ready`, ID модели, версия набора, срез и диагностические MAE/покрытие. Все пять товаров готовятся на этом тестовом наборе. Ошибки синтетики не доказывают реальное превосходство ML.
- Повторите обучение и обновите модели: прежний ID, без новой версии для того же среза. Обучите также на срезе `2026-10-04`: получатся две версии. Верните срез `2026-10-11`.
- Получите прогноз ML: для пяти товаров видны ML, конечные неотрицательные числа, B1 для сравнения и даты истории.
- Выберите ML в производственном плане, оставьте день открытым и рассчитайте. Проверьте отображение исторического воспроизведения, партий и ID модели. Измените p1 на 84, подтвердите, экспортируйте CSV. В файле проверьте `confirmed_qty`, `model_id`, `protocol_version`, `dataset_version`, `bakery_id`, `target`, `unit`.
- Полностью остановите API и запустите с прежним `BAKEPLAN_DB`. Перезагрузите страницу. Через «Продолжить работу с сохранённым набором» загрузите набор и обновите модели; через историю откройте подтверждённый план. ID, прогноз, количества и редакция должны сохраниться.
- Импортируйте тот же файл для `dias-qa-b`: новый набор, пустой список моделей. Он не должен автоматически использовать модель `dias-qa-a`. Исходный план и версии первого набора остаются прежними.

## Безопасные отказы

- Закройте целевой день, рассчитайте ML-план: нет прогноза выпуска, рекомендации 0, предупреждение; подтверждение положительного количества запрещено.
- Для переноса создайте отдельную синтетическую копию командой выше с `synthetic_csv(guard='carryover')`. Импортируйте её и обучите: p1 должен остаться ручным с рекомендацией 0 и объяснением, даже при наличии модели.
- Аналогично `synthetic_csv(guard='unknown')`: у p1 более половины последних наблюдаемых дней с неизвестным наличием; автоматический выпуск отключён.
- `synthetic_csv(21)` даёт корректный короткий набор: обучение возвращает `not_ready`, прогноз сохраняет явный fallback. Это не частичная ошибка импорта.
- В отдельной копии нарушьте баланс или повторите одну строку: импорт полностью отклонён, без нового набора. Срез в будущем и срез не раньше даты прогноза также отклоняются понятным сообщением.
- Через `/docs` выберите ID модели первой пекарни для второй, затем модель с более поздним срезом: ожидается 422. Повтор ключа обучения с другим срезом: 409. Исходные версии и план не меняются.
- Нажмите «Демо строк продаж», замените ID пекарни на `dias-sales-qa`, импортируйте. Выберите вчерашний срез и следующую дату. Обучение/прогноз доступны в `item_line`; производственный план и подтверждение отсутствуют. Прямой запрос `/api/plans` для этого набора получает 422.
- Во время долгого запроса проверьте блокировку повторных кнопок и смены набора. После успеха и ошибки интерфейс снова доступен; старый результат не должен выглядеть рассчитанным для новых полей.

## Автоматические проверки

```sh
.venv/bin/python -m pytest backend/tests/test_ml_api.py -q
.venv/bin/python -m pytest backend/tests -q
.venv/bin/python -m ruff check backend
cd frontend
npm run lint
npm run typecheck
npm test
npm run build
```

API-тесты сами генерируют CSV, используют временную SQLite, закрывают/снова открывают TestClient для проверки сохранности, проверяют таймаут и занятость без частичной записи, повреждение JSON/снимка, изоляцию целей и пекарен. Повреждение хранилища моделируется только внутри временной тестовой базы.

Сквозной браузерный набор запускайте из корня по [руководству разработчика](DEVELOPMENT.md): `npm ci`, `npx playwright install chromium`, `npm run test:e2e`. При блокировке окружением запишите точный предел; не отмечайте невыполненный этап как пройденный. В итоговом протоколе отдельно отметьте автоматические тесты, ручной restart и ошибки. Реальные данные пилота и новое независимое измерение точности остаются отдельной работой владельца данных и команды. Отдельно проверяйте реальную задержку учёта: рабочая пара «завтра / вчера» и новый holdout имеют горизонт t−2. Смените дату так, чтобы разрыв со срезом был 1 или 3 дня: должно появиться предупреждение о неприменимости двухдневной оценки. В старых сохранённых моделях v1 этот контракт не действует; должен использоваться явный fallback или новая модель v2.


## Дополнительная проверка стабилизации

- После получения прогноза измените дату, срез или метод: старое число должно иметь явное предупреждение и не выглядеть новым расчётом. Пересчитайте.
- После расчёта плана измените метод/дату/срез/календарь: подтверждение старого снимка заблокировано до нового расчёта. Откройте сохранённый план из истории, проверьте его параметры и подтверждённое количество.
- После успешного подтверждения временно заблокируйте только обновление истории в инструментах браузера. Результат подтверждения должен остаться сохранённым; сообщение предлагает обновить историю, не утверждает, что запись не состоялась.
- У каждого товара различимы прогноз, допустимая рекомендация, редактируемое количество и фактически сохранённое подтверждение. IDs/хеши доступны в подробностях; метод и ограничения видны без них.
- Проверьте ширину ноутбука и телефона: поля и действия читаемы, таблица прокручивается внутри секции, страница не обрезается. Это ручная проверка, её нельзя заменить успешной сборкой.
- Проверку HTTPS, анонимного отказа, второго устройства, server restart и backup/restore в целевой среде выполняйте по [DEPLOYMENT](DEPLOYMENT.md). До выбора хоста эти пункты открыты.
