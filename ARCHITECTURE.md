# Архитектура BakePlan

React собирает параметры заказа, FastAPI строит план для выбранного набора данных, а SQLite хранит его версии. В каждом новом плане закупки сохраняются учтённые к открытию поставки и объяснение рекомендованного количества.

## 1. Единые правила расчёта и проверки заказа

Реализовано в версии `procurement-3`. Для каждого товара BakePlan выбирает прогноз продаж и затем один раз рассчитывает заказ. B1, ML и возврат к B1 используют одну функцию. Она прибавляет поступления к известному остатку, округляет непокрытую потребность до целых упаковок и применяет лимит. Если остаток неизвестен, сотрудник задаёт количество вручную. В закрытый день заказ равен нулю. [Расчёт позиции](backend/procurement_planning.py)

Например, при прогнозе 11 штук, нулевом остатке, упаковке по 6 и лимите поставщика 6 BakePlan рекомендует одну упаковку. До прогноза не хватает 5 штук. Если сотрудник изменит заказ на 0, нехватка составит 11 штук, и одну упаковку ещё можно добавить. В плане и CSV сохраняются оба решения с отдельными количествами и причинами. Старые редакции по-прежнему выгружаются в своём формате.

Браузер показывает сохранённое объяснение. Во время ручного ввода он пересчитывает нехватку сразу, а при подтверждении её проверяет сервер. Тесты Python и TypeScript читают одни и те же примеры, включая неизвестный остаток, известный ноль, закрытый день и лимит меньше упаковки. [Общие примеры расчёта](fixtures/procurement_order_cases.json)

## 2. Реестр поставок по филиалам

Реализовано в версии расчёта `procurement-4`. Реестр хранится в SQLite отдельно от импортов продаж. Ключ строки состоит из кода филиала, номера накладной и кода товара. При повторной загрузке данных того же филиала его поставки остаются доступны. В другой точке может использоваться тот же номер накладной. [Реестр и приёмка](backend/deliveries.py)

Каждая приёмка записывается в одной транзакции с обновлением принятого количества. Ключ операции позволяет безопасно повторить запрос после потери связи. Например, после приёмки 5 из 12 бутылок остаток партии равен 7. Отмена закрывает оставшиеся 7 и сохраняет факт приёмки первых 5.

Рабочий расчёт читает неполученные партии нужного филиала с ожидаемой датой от дня заказа до даты продаж включительно. За одну транзакцию он сохраняет план и снимок учтённых партий с идентификаторами, номерами, датами и количеством. Позднейшая приёмка, перенос или отмена меняют следующие расчёты. Старые планы и CSV воспроизводятся из своих снимков. Для исторического расчёта используется ручной список поставок на дату сценария.

## 3. Один срез истории на пакет прогнозов

Для одного ML-прогноза BakePlan один раз отбирает и нормализует наблюдения по дату среза включительно и строит индекс по товарам. Если модель обучена раньше, контрольная сумма считается только по строкам, доступным в день обучения. Более свежие продажи участвуют в прогнозе. Индекс действует в пределах одного запроса. При проверке модели на исторических данных новый индекс строится для каждой даты прогноза. [Подготовка истории](backend/ml_core.py) · [Прогноз для всех товаров](backend/ml_service.py)

На 50 товарах и 10 000 синтетических строках закупок медиана времени вызова `forecast_items` сократилась с **3,349 с до 67,5 мс** (в **49,6 раза**). Измеряли на Windows 11, Intel Core i7-1355U, Python 3.14.3. Обе версии читали одну обученную модель из SQLite. Между датой обучения и срезом прогноза было 7 дней. После прогрева каждой версии выполнили по пять замеров, чередуя порядок. Измерение включает чтение модели и расчёт всех позиций. Все полные ответы совпали после сортировки ключей JSON, включая даты наблюдений и причины перехода на B1. Для 25 товаров обе версии выбрали ML, для остальных 25 — B1.

Для повторения замера из корня репозитория на Windows с установленными зависимостями выполните команды ниже. Скрипт обучает модель один раз до замеров и сравнивает ответы с предыдущей версией. [Скрипт сравнения](tools/benchmark_batch_forecast.py)

```powershell
git worktree add --detach ../bakeplan-before-history 09eb023058b836a683f822a3051b42904d97124a
.\.venv\Scripts\python.exe tools/benchmark_batch_forecast.py ../bakeplan-before-history
```

## 4. Подготовка заказа до блокировки записи

Раньше расчёт заказа на 50 товаров 50 раз просматривал историю из 10 000 строк, удерживая общую для филиалов блокировку записи SQLite. Теперь BakePlan группирует историю по товарам за один проход и заранее рассчитывает прогнозы и показатели доступности. Когда начинается транзакция записи, остаётся прочитать актуальные поставки, применить их к количествам заказа и сохранить первую редакцию. [Подготовка позиций](backend/procurement_planning.py) · [Сохранение заказа](backend/services.py)

Если во время подготовки сотрудник принимает 5 из 12 бутылок, заказ учитывает оставшиеся в пути 7. Тест выполняет обе операции через API и проверяет количество в заказе и в сохранённой редакции. [Проверка параллельной приёмки](backend/tests/test_procurement_preparation.py)

| Медианное время | До | После |
|---|---:|---:|
| Создание и сохранение заказа B1 | 66,5 мс | 45,4 мс |
| Удержание блокировки записи при B1 | 45,2 мс | 14,8 мс |
| Создание и сохранение заказа ML | 125,9 мс | 107,5 мс |
| Удержание блокировки записи при ML | 41,5 мс | 9,7 мс |

В отдельном контрольном запуске полный заказ ML занял 119,5 и 121,2 мс соответственно. Время удержания блокировки в этом запуске сократилось с 35,1 до 15,3 мс.

Сравнение выполнено на Windows 11, Intel Core i7-1355U, Python 3.14.3. В обеих версиях использовались одни и те же 10 000 синтетических строк, 50 товаров, обученная модель и реестр с частично принятой поставкой. В заказе ML модель использовалась для 25 товаров, ещё 25 получили прогноз B1. После прогрева выполнили семь пар замеров, чередуя порядок версий. Время блокировки измерялось от успешного получения права записи до завершения фиксации в SQLite. Скрипт проверяет формат новых идентификаторов и времени UTC, сравнивает все остальные поля заказа между версиями и сверяет каждый ответ с первой редакцией в базе. [Скрипт сравнения](tools/benchmark_procurement_plan.py)

```powershell
git worktree add --detach ../bakeplan-before-order 70b093916ee0cd9590917ebb35ba4d8300b16ede
.\.venv\Scripts\python.exe tools/benchmark_procurement_plan.py ../bakeplan-before-order
```
