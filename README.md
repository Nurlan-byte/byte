# BakePlan

Локальный прототип: CSV → проверка → B0/B1 или экспериментальный B1 + Ridge → допустимые партии → ручное подтверждение → SQLite → история и CSV. Интерфейс на русском, пять изделий в целых штуках для операционного пути. Наборы и модели изолированы по пекарне, версии данных и единице измерения; это не многопользовательский сервис. История пекарни не предоставлена; все публичные примеры синтетические. Точность, экономия и коммерческая готовность не заявляются.

Рабочий контракт: план сегодня на завтра, полные факты только по вчера включительно, то есть t−2. Интегрированная модель и её holdout теперь используют одинаковый двухдневный горизонт, с обучающим срезом не позже первого cutoff оценки. Новый протокол `pooled-relative-ridge-200-v3-horizon-2-experimental` (одна Ridge-модель на все товары, признаки в долях от B1) не наследует показатели v1/v2. При другом разрыве между датой и срезом UI явно предупреждает, что эта оценка неприменима. MAE B1 и ML, парное N, покрытие и даты сравнения доступны по каждому товару. [Процедура независимой будущей оценки](docs/EVALUATION.md).

## ML в приложении

Теперь можно импортировать набор с явными `bakery_id`, `target`, `unit`, `provenance`, обучить локальную модель, увидеть её статус и временную оценку, получить прогноз и выбрать ML в плане. Нет подходящей модели/истории — явный B1 или ручная заготовка, а не скрытый прогноз нуля. B1 остаётся методом по умолчанию. Готовность модели означает техническую возможность расчёта, не преимущество по точности.

- `history-1`: `sold_units / physical_unit`, баланс, stockout и перенос остатков сохраняют прежние защиты.
- `sales-1`: `item_line_count / item_line`, только прогноз наблюдаемых строк товара. Этот путь не создаёт физический выпуск и не выдумывает остатки/waste. BreadBasket относится именно к sales-only пути.
- JSON-артефакт привязан к набору, snapshot hash, cutoff и версии протокола. Никаких загрузок pickle/joblib. Обучение ограничено 60 секундами, 10 000 строками и 50 товарами; сервер выполняет одно обучение одновременно.
- Старый импорт без явных метаданных продолжает работать с B0/B1; для ML его нужно повторно импортировать с корректным происхождением и единицей.

Практическое руководство и шаблоны: [docs/ML_INTEGRATION.md](docs/ML_INTEGRATION.md). Ручная проверка для Диаса: [docs/manual-qa.md](docs/manual-qa.md).

Это новая фиксированная реализация pooled relative Ridge α=200 с безопасным JSON-форматом; дизайн выбран только на сгенерированных данных. Она не тождественна старому исследовательскому pipeline и не наследует его показатели. Уже просмотренный BreadBasket test остаётся историческим экспериментом, не новым независимым тестом.

## Быстрый запуск

Начать утром: [короткий checklist](docs/MORNING_CHECKLIST.md). Для резервного показа на Windows: [Docker Desktop + WSL2, постоянная SQLite, backup/restore](docs/LOCAL_WINDOWS.md). Ниже — проверяемый нативный путь без Docker. Это инструкции для запуска владельцем; состояние его ноутбука и Docker Desktop здесь не проверялось.

Нужны Git, Python 3.14 и Node.js 24 с npm. Для чистой установки:

```sh
git clone https://github.com/Nurlan-byte/byte.git bakeplan
cd bakeplan
git rev-parse HEAD
```

Запишите SHA для протокола проверки. Дальше выполняйте команды из корня репозитория. PowerShell на Windows:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock
cd frontend
npm.cmd ci
cd ..
```

Терминал 1:

```powershell
$env:BAKEPLAN_DB = "data/bakeplan.sqlite3"
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Терминал 2:

```powershell
cd frontend
npm.cmd run dev
```

Откройте http://127.0.0.1:5173. API и интерактивная схема: http://127.0.0.1:8000/docs. База создаётся автоматически; путь относителен к рабочему каталогу сервера. Перезапускайте сервер из того же корня с тем же `BAKEPLAN_DB`. `.env.example` — пример переменных, автоматического чтения `.env` нет. Перед обновлением сделайте проверенную резервную копию SQLite по [инструкции backup/restore](docs/DEPLOYMENT.md). Текущая схема SQLite — PRAGMA user_version=3. Старая v0/v1 БД сначала получает резервную копию <имя>.pre-v2.bak и мигрирует до v2; перед добавлением неизменяемых моделей и ключей обучения существующая БД получает <имя>.pre-v3.bak. Новая пустая БД создаётся сразу без лишних backup. Старые dataset_id, дубликаты, планы, редакции и подтверждения сохраняются; повторный импорт ссылается на самый ранний канонический набор, а старые ссылки не переписываются. Повторный запуск миграцию не повторяет. Если backup уже существует при незавершённой миграции, сервер остановится: сначала проверьте БД и резервную копию, не удаляйте их вслепую. Работайте на локальном постоянном диске.

Linux/macOS, из корня:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.lock
npm --prefix frontend ci
BAKEPLAN_DB=data/bakeplan.sqlite3 .venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

В другом терминале: `npm --prefix frontend run dev`. Не открывайте dev-сервер наружу. Для сборки frontend: `npm --prefix frontend run build`; каталог `frontend/dist` сам по себе не запускает API. Production-прокси маршрутизирует `/api` в FastAPI и остальные пути в собранный frontend, см. [DEPLOYMENT](docs/DEPLOYMENT.md). Фактические проверки Windows и Linux CI указаны в [VERIFICATION](VERIFICATION.md).

## Первый полный сценарий

1. Откройте раздел **Данные**, загрузите демо или `fixtures/synthetic_demo.csv`, выберите источник **synthetic** и импортируйте. Проверьте диагностику. Ошибка отклоняет файл целиком.
2. В разделе **План** (стартовый экран, B1 по умолчанию) для актуального двухдневного контракта укажите дату `2026-10-13`, срез `2026-10-11`; после 13 октября это историческое воспроизведение. При необходимости откройте **Модель**, обучите модель, дождитесь статуса, получите прогноз и проверьте фактический метод по товарам. В плане по умолчанию B1; для проверки интеграции выберите ML. Если модели нет, причина fallback видна явно.
3. Измените p1 на 84. Количество 90 и 100 недопустимо: партия 12, предел 100 → разрешённый максимум 96. Прогноз, рекомендация, ручное поле и сохранённое значение показаны отдельно; изменения сохраняются кнопкой подтверждения. Переключение разделов не сбрасывает черновик, но перезагрузка страницы сбросит ещё не сохранённые поля.
4. Подтвердите, обновите страницу, откройте **История → Обновить историю → Открыть план**, экспортируйте CSV. Перезапустите API: план остаётся в той же SQLite.
5. В **Данных** импортируйте `fixtures/invalid_balance.csv`: ожидается ошибка баланса без частичной записи.

Историческая численная контрольная точка B1: target `2026-10-12`, cutoff `2026-10-11` даёт p1=65 и рекомендацию60; B0=80 и рекомендацию84. Это отдельный однодневный replay для регрессии, не рабочий двухдневный горизонт и не подтверждение новой ML-оценки.

Для нового рабочего дня выберите явную дату и срез. Срез включителен, но сервер консервативно разрешает только календарные дни строго раньше сегодня в Asia/Qyzylorda (UTC+5): полный итог сегодняшнего дня пока не используется. Предполагается, что итог завершённого дня доступен после его окончания; фактического timestamp доступности нет. При задержке учёта сдвиньте срез ещё назад. Это допущение, а не проверка времени публикации каждого факта. Прошлую дату можно подтвердить только с явной меткой replay. Рабочий черновик после наступления целевого дня подтверждать нельзя; безопасный повтор ранее успешного запроса возвращает его прежний результат.

Флаг «Целевой день открыт» задаётся явно. Только явный target_is_open=false даёт выпуск0 без прогноза; факты целевого дня после cutoff никогда не читаются для определения календаря; сервер не допускает ручного увеличения. Владелец проверяет календарь до расчёта, полноценного календарного сервиса здесь нет. Если более50% наблюдаемых открытых дней за56 дней имеют occurred/unknown, рекомендация отключена: ручная заготовка0 и предупреждение. Диагностический baseline может оставаться видимым; это не автоматическое решение. Порог50% — фиксированное правило безопасности прототипа, не научная гарантия.

## Исторические offline-эксперименты

После работающего базового потока добавлен небольшой локальный `PoissonRegressor`. Он запускается отдельно, не выдаёт производственных рекомендаций и не заменяет B0/B1 в API:

```powershell
.\.venv\Scripts\python.exe -m pip install -r tools/requirements.lock
.\.venv\Scripts\python.exe -m unittest discover -s tools/tests -v
.\.venv\Scripts\python.exe tools/evaluate.py fixtures/synthetic_demo.csv --source synthetic --split-date 2026-09-28 --output private/local-report.json
```

Разделение по датам для всех товаров, календарные лаги7/14, преобразования обучаются только на train. Проверка на поздних датах с последовательным обновлением наблюдаемой истории; модель не переобучается на holdout. При недостатке истории явный отказ. Подробные допущения — [tools/README.md](tools/README.md). Этот синтетический эксперимент не доказывает качество ML, выбор лучшего метода или экономию. Реальная оценка и независимый final test остаются следующей работой.

## Границы и продолжение

В приложении нет пользовательских аккаунтов и границ доступа между пекарнями. Подготовленный внешний gateway ограничивает всё демо одним контролируемым доступом; это не многопользовательская авторизация. Локальный API запускается только на127.0.0.1; в Docker он доступен лишь во внутренней сети и никогда не публикуется напрямую. Нет производственного расписания, кассовой интеграции, восстановления скрытого спроса, доказанного эффекта ML или денежной экономии. Публичное размещение допускается только после выполнения checklist [DEPLOYMENT](docs/DEPLOYMENT.md). Дальше: получить разрешённую историю и описание доступности данных, согласовать ассортимент/перенос остатков, провести независимый запуск, временную оценку и наблюдательный пилот. Регламент конкурса команда проверяет отдельно.

Ответственности и AI-атрибуция: [CONTRIBUTING.md](CONTRIBUTING.md).

## Исторический sales-only исследовательский путь

Добавлен отдельный CLI для исправленного BreadBasket: [протокол и команды](tools/SALES_ONLY.md). Он оценивает item-line occurrences, не создаёт вымышленные остатки/stockout и не меняет рабочий план. Внешние CSV и отчёты остаются приватными; публичный пример полностью синтетический. B0/B1 и Poisson сравниваются на одинаковых датах, с явным rolling history и чувствительностью к предполагаемым нулям.
