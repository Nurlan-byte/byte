# BakePlan

Локальный прототип: CSV → проверка → B0/B1 или экспериментальный B1 + Ridge → допустимые партии → ручное подтверждение → SQLite → история и CSV. Интерфейс на русском, пять изделий в целых штуках для операционного пути. Наборы и модели изолированы по пекарне, версии данных и единице измерения; это не многопользовательский сервис. История пекарни не предоставлена; все публичные примеры синтетические. Точность, экономия и коммерческая готовность не заявляются.

## ML в приложении

Теперь можно импортировать набор с явными `bakery_id`, `target`, `unit`, `provenance`, обучить локальную модель, увидеть её статус и временную оценку, получить прогноз и выбрать ML в плане. Нет подходящей модели/истории — явный B1 или ручная заготовка, а не скрытый прогноз нуля. B1 остаётся методом по умолчанию. Готовность модели означает техническую возможность расчёта, не преимущество по точности.

- `history-1`: `sold_units / physical_unit`, баланс, stockout и перенос остатков сохраняют прежние защиты.
- `sales-1`: `item_line_count / item_line`, только прогноз наблюдаемых строк товара. Этот путь не создаёт физический выпуск и не выдумывает остатки/waste. BreadBasket относится именно к sales-only пути.
- JSON-артефакт привязан к набору, snapshot hash, cutoff и версии протокола. Никаких загрузок pickle/joblib. Обучение ограничено 60 секундами, 10 000 строками и 50 товарами; сервер выполняет одно обучение одновременно.
- Старый импорт без явных метаданных продолжает работать с B0/B1; для ML его нужно повторно импортировать с корректным происхождением и единицей.

Практическое руководство и шаблоны: [docs/ML_INTEGRATION.md](docs/ML_INTEGRATION.md). Ручная проверка для Диаса: [docs/manual-qa.md](docs/manual-qa.md).

Это новая фиксированная реализация per-product Ridge α=100 с безопасным JSON-форматом. Она не тождественна старому исследовательскому pipeline и не наследует его показатели. Уже просмотренный BreadBasket test остаётся историческим экспериментом, не новым независимым тестом.

## Быстрый запуск

Нужны Python 3.14 и Node.js 24 с npm. Выполняйте команды из корня репозитория. PowerShell на Windows:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock
cd frontend
npm.cmd ci
cd ..
```

Терминал 1:

```powershell
$env:BAKEPLAN_DB = "data/bakeplan.sqlite3"
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Терминал 2:

```powershell
cd frontend
npm.cmd run dev
```

Откройте http://127.0.0.1:5173. API и интерактивная схема: http://127.0.0.1:8000/docs. База создаётся автоматически; путь относителен к рабочему каталогу сервера. Перезапускайте сервер из того же корня с тем же `BAKEPLAN_DB`. `.env.example` — пример переменных, автоматического чтения `.env` нет. Сделайте резервную копию SQLite при остановленном сервере. Текущая схема SQLite — PRAGMA user_version=3. Старая v0/v1 БД сначала получает резервную копию <имя>.pre-v2.bak и мигрирует до v2; перед добавлением неизменяемых моделей и ключей обучения существующая БД получает <имя>.pre-v3.bak. Новая пустая БД создаётся сразу без лишних backup. Старые dataset_id, дубликаты, планы, редакции и подтверждения сохраняются; повторный импорт ссылается на самый ранний канонический набор, а старые ссылки не переписываются. Повторный запуск миграцию не повторяет. Если backup уже существует при незавершённой миграции, сервер остановится: сначала проверьте БД и резервную копию, не удаляйте их вслепую. Работайте на локальном постоянном диске.

Linux/macOS: `python3 -m venv .venv`, `.venv/bin/python -m pip install -r backend/requirements.lock`, `.venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000`; используйте `npm` вместо `npm.cmd`. Исторические проверки выполнены на Windows; текущие проверки cloud Linux и ограничения браузера указаны в VERIFICATION.md.

## Первый полный сценарий

1. Загрузите демо или `fixtures/synthetic_demo.csv`, выберите источник **synthetic** и импортируйте. Проверьте диагностику. Ошибка отклоняет файл целиком.
2. Для фиксированного примера укажите дату `2026-10-12`, срез `2026-10-11`, метод B1. Это историческое воспроизведение. У p1 прогноз 65 штук, рекомендация 60; B0 даёт 80 и рекомендацию 84.
3. Измените p1 на 84. Количество90 и100 недопустимо: партия12, предел100 → разрешённый максимум96.
4. Подтвердите, обновите страницу, откройте план из истории, экспортируйте CSV. Перезапустите API: план остаётся в той же SQLite.
5. Импортируйте `fixtures/invalid_balance.csv`: ожидается ошибка баланса без частичной записи.

Для нового рабочего дня выберите явную дату и срез. Срез включителен, но сервер консервативно разрешает только календарные дни строго раньше сегодня в Asia/Qyzylorda (UTC+5): полный итог сегодняшнего дня пока не используется. Предполагается, что итог завершённого дня доступен после его окончания; фактического timestamp доступности нет. При задержке учёта сдвиньте срез ещё назад. Это допущение, а не проверка времени публикации каждого факта. Прошлую дату можно подтвердить только с явной меткой replay. Рабочий черновик после наступления целевого дня подтверждать нельзя; безопасный повтор ранее успешного запроса возвращает его прежний результат.

Флаг «Целевой день открыт» задаётся явно. Только явный target_is_open=false даёт выпуск0 без прогноза; факты целевого дня после cutoff никогда не читаются для определения календаря; сервер не допускает ручного увеличения. Владелец проверяет календарь до расчёта, полноценного календарного сервиса здесь нет. Если более50% наблюдаемых открытых дней за56 дней имеют occurred/unknown, рекомендация отключена: ручная заготовка0 и предупреждение. Диагностический baseline может оставаться видимым; это не автоматическое решение. Порог50% — фиксированное правило безопасности прототипа, не научная гарантия.

## CSV v1

UTF-8, разделитель запятая, ISO-дата `YYYY-MM-DD`, обязательные столбцы:

```csv
date,product_id,is_open,opening,produced,sold,waste,closing,other_out,stockout_status
2026-10-05,p1,true,0,100,80,20,0,0,none
```

`product_id` — строковый стабильный ключ p1…p5, название не ключ. `is_open`: true/false или1/0. Количества — неотрицательные целые не более 1 000 000 000; более узкие ML-границы указаны в руководстве. Баланс: opening+produced=sold+waste+closing+other_out. `stockout_status`: none/occurred/unknown; closing0 после waste не доказывает дефицит. Дубликат дата/товар, неизвестный товар, дробь, отрицательное число или неверный баланс отклоняются. Пропуск не становится продажей0; закрытый день задаётся явно. Каталог фиксирован в `backend/config.py`; смена каталога требует новой версии и проверки контракта.

B0 берёт только пригодный день ровно за7 календарных дней. B1 усредняет до4 последних пригодных таких же дней недели за56 дней. Пригодность: открыто, stockout none, дата не позже среза. Источники и число наблюдений сохраняются. Недостаточная история помечается; без истории выдаётся ручная заготовка0, а не прогноз0. Округление к ближайшей партии, равное расстояние вниз; затем ограничение максимальной разрешённой партией. Прогноз, рекомендация и подтверждённый выпуск хранятся отдельно. Общую загрузку печи управляющий проверяет вручную. Денежной оптимизации нет: затраты неизвестны.

Наборы неизменяемы. Поддерживаемые schema_version — history-1 (по умолчанию) и отдельная sales-1; неизвестная версия отклоняется. Повтор одинакового CSV с теми же source, schema_version и явно указанными bakery_id/target/unit/provenance возвращает существующий dataset_id (HTTP200); новый импорт — HTTP201. Исправления содержимого получают новый набор. План хранит снимок версии данных и параметров. Подтверждение атомарно; revision защищает от устаревшего экрана, idempotency_key возвращает исходный результат при повторе того же запроса и конфликтует при изменённом теле. Прошлые редакции доступны через API. Бизнес-данные, SQLite и секреты исключены из Git. Не загружайте pickle/joblib; поддерживается только CSV.

## Отдельный эксперимент ML

После работающего базового потока добавлен небольшой локальный `PoissonRegressor`. Он запускается отдельно, не выдаёт производственных рекомендаций и не заменяет B0/B1 в API:

```powershell
.\.venv\Scripts\python.exe -m pip install -r tools/requirements.lock
.\.venv\Scripts\python.exe -m unittest discover -s tools/tests -v
.\.venv\Scripts\python.exe tools/evaluate.py fixtures/synthetic_demo.csv --source synthetic --split-date 2026-09-28 --output private/local-report.json
```

Разделение по датам для всех товаров, календарные лаги7/14, преобразования обучаются только на train. Проверка на поздних датах с последовательным обновлением наблюдаемой истории; модель не переобучается на holdout. При недостатке истории явный отказ. Подробные допущения — [tools/README.md](tools/README.md). Этот синтетический эксперимент не доказывает качество ML, выбор лучшего метода или экономию. Реальная оценка и независимый final test остаются следующей работой.

## Границы и продолжение

Нет аутентификации, многопользовательского доступа, производственного расписания, кассовой интеграции, восстановления скрытого спроса, доказанного эффекта ML или денежной экономии. API запускается только на127.0.0.1. Не публикуйте этот сервер без отдельного проектирования доступа и защиты данных. Дальше: получить разрешённую историю и описание доступности данных, согласовать ассортимент/перенос остатков, провести независимый запуск, временную оценку и наблюдательный пилот. Регламент конкурса команда проверяет отдельно.

Ответственности и AI-атрибуция: [CONTRIBUTING.md](CONTRIBUTING.md).

## Контракт и структура после рефакторинга

`backend/imports.py` — общий строгий CSV, `forecasting.py` — чистые B0/B1; `planning.py` — партии и допуск автоматической рекомендации; `services.py` — прикладные сценарии, `storage.py` — SQLite и миграция, `schemas.py/config.py` — вход и каталог. Подтверждение сохраняет один BEGIN IMMEDIATE: повторный ключ проверяется до даты/revision, затем результат, снимок и редакция записываются вместе. Frontend разделён на import/planning/history, типы и API-клиент; Redux и ORM не добавлялись.

Численный baseline использует пригодные открытые дни stockout=none и активные даты каталога. Перенос opening/closing среди наблюдаемых открытых дней за56 дней или stockout/unknown более50% отключает автоматическую рекомендацию, но диагностический baseline сохраняется. Offline использует то же численное ядро, но явно исключает opening>0 из эксперимента; closing>0 сам по себе не исключает численную оценку продаж. Эти политики также действуют при явном выборе ML в рабочем плане. Каталог API разрешает только p1…p5; offline допускает другие строковые ID и сам задаёт период исторической оценки. Формат/баланс/закрытый день проверяются одинаково.

Списки `GET /api/datasets` и `GET /api/plans` возвращают краткие метаданные без rows/items; limit по умолчанию20, максимум100, offset>=0. Порядок — устойчивый порядок создания (последние первыми); новый импорт/план может сдвинуть offset, обновите первую страницу. Детали: `/api/datasets/{id}` и `/api/plans/{id}`. В UI есть следующая/предыдущая страница истории.

Ошибки имеют JSON `error: {code, message, details}`, включая413 при теле больше2МБ. API-клиент также показывает безопасное сообщение для не-JSON ответа прокси. Строка CSV ограничена1млн символов, максимум10000 записей; закрытый день с ненулевыми produced/sold отклоняется обеими реализациями.

## Sales-only исследовательский путь

Добавлен отдельный CLI для исправленного BreadBasket: [протокол и команды](tools/SALES_ONLY.md). Он оценивает item-line occurrences, не создаёт вымышленные остатки/stockout и не меняет рабочий план. Внешние CSV и отчёты остаются приватными; публичный пример полностью синтетический. B0/B1 и Poisson сравниваются на одинаковых датах, с явным rolling history и чувствительностью к предполагаемым нулям.
