# Открытие заказа во время обновления филиалов

Критерий на локальном стенде: 60 из 60 открытий подтверждённого заказа возвращают правильную версию, филиал и количества. При пяти открытиях в секунду за 12 секунд 95-й процентиль времени ответа API должен быть не выше 500 мс. Этот же предел применяется к открытиям, полностью попавшим в период работы четырёх обновлений. Отсутствие пересечения считается провалом проверки.

## Воспроизведение

Установите зависимости сервера, подготовьте закреплённые веса командой `python -m backend.chronos_assets` и установите [Grafana k6 v2.4.0](https://github.com/grafana/k6/releases/tag/v2.4.0). Из корня проекта:

```powershell
python tools/load/confirmed_orders.py --k6 k6 --output test-results/order-load.json
```

Стенд создаёт временную базу, тестовый ключ и сервер на случайном порту `127.0.0.1`. Фиктивная касса выдаёт каждому из четырёх филиалов 28 дней продаж одного товара. Календарь и погода пустые. Сценарий подключает филиалы, задаёт упаковку и подтверждает четыре заказа через API. До замера модель прогрета этим потоком. В измеряемый период стенд запускает четыре обычных обработчика очереди обновления на следующую бизнес-дату. Рабочее приложение обычно запускает один обработчик на процесс. Здесь их четыре одновременно, чтобы проверить конкуренцию за ресурсы. Фиксированная задержка ответа кассы в 4 секунды позволяет воспроизвести пересечение. Расчёт Chronos-2, запись SQLite и чтение заказов выполняются обычным кодом приложения.

После нагрузки стенд считывает через API обновлённые снимки всех филиалов и проверяет даты, идентификаторы, выбранный метод и наличие численного прогноза. `concurrent_reads` считает чтения, полностью выполненные после входа всех четырёх работников в импорт и до возврата первого работника. `inference_overlapping_reads` отдельно показывает, сколько HTTP-чтений по времени пересеклось с фактическим выполнением модели. Ноль в этом поле означает, что в этом прогоне в короткое окно вычисления ни один запрос не попал. Времена клиента и сервера снимаются на одной машине. Показатели относятся к чтению API с прогретой моделью. Время рендеринга интерфейса, загрузки весов при холодном старте и сроки обслуживания реальных филиалов измеряются отдельно.

Для сравнения с более ранней версией используйте тот же Python, k6, веса модели и этот же файл сценария. Запустите его по абсолютному пути из корня нужной версии. Чередуйте версии, запускайте по одному прогону и сравнивайте медианы нескольких прогонов. ## Сравнение при выделении общего расчёта прогноза

Замер 21 ноября 2026 года на одном компьютере с Windows и локальными весами Chronos-2, по три прогона на версию. В каждой строке проверены все 180 открытий заказов.

| Версия | p95 по прогонам, мс | Прогоны с p95 ≤ 500 мс |
|---|---:|---:|
| До, `f0cf5a4` | 7,05 / 7,79 / 820,44 | 2 из 3 |
| С общим расчётом | 260,09 / 7,86 / 106,34 | 3 из 3 |

В новой версии за прогон 20–25 открытий полностью попали в период работы четырёх обработчиков. Из 60 открытий с вычислением самой модели пересеклись 2–6. Все четыре обновлённых прогноза в каждом из трёх прогонов считаны обратно. Значения по четырём филиалам совпали с исходной версией.

Порог в исходной версии был превышен при корректных ответах на все 60 чтений. В двух дополнительных прогонах на версию с раздельным измерением времени клиента, приложения и чтения базы задержка не повторилась: p95 составил 7,28 и 5,58 мс до изменения, 6,41 и 6,46 мс после. Причина прежнего скачка остаётся неизвестной. Эти измерения дают проверку предельного времени под заданной нагрузкой. Данных для вывода об ускорении чтения заказов или выполнении производственного SLO пока недостаточно.

Проверка самого сценария проводилась на отдельной копии стенда. При намеренно неверной ожидаемой версии заказа и двухсекундной блокировке тестовой базы k6 отклонил результат: 0 из 58 ответов прошли сверку, 2 открытия пропущены, p95 составил 1 399 мс. Команда вернула ненулевой код и сохранила причины отказа в JSON.
