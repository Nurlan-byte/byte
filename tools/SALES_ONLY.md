# Отдельная оценка sales-only

Это исследовательский CLI. Он не вызывает API импорта/планирования, не записывает SQLite и не выдаёт confirmed_qty. Цель item_line_count — число товарных строк транзакций на наблюдаемую дату. Это не проверенное количество изделий и не неограниченный спрос.

## Источник

[Kaggle akashdeepkuila/bakery](https://www.kaggle.com/datasets/akashdeepkuila/bakery), версия2. Используйте исправленный `bakery_sales_revised.csv`; исходный `Bakery.csv` содержит проблему смешанных дат и не поддерживается этим адаптером. Uploader указывает CC0: Public Domain; полная цепочка владения независимо не проверена. Источник не является пилотом пекарни Тараза и не подтверждает локальную пользу. URL, версия и SHA256 — [sales_source.json](sales_source.json).

CSV храните вне репозитория. Повторяющиеся Transaction/Item/date_time строки считаются отдельными line occurrences: точные физические количества из этого нельзя восстановить. Парсер сохраняет строковые идентификаторы транзакций и принимает MM/DD/YYYY HH:MM[:SS]. Поля period_day/weekday_weekend не используются как признаки; weekday вычисляется из исправленной даты. Stockout, production, opening, closing и waste не создаются.

## Замороженный протокол

До обучения зафиксированы train до2017-01-31, validation2017-02-01…2017-02-28, test2017-03-01…2017-04-09. Пять пищевых позиций выбираются по доле положительных наблюдаемых дат только в train, при равенстве — по имени. Allowlist пищевых названий заранее задан в адаптере; напитки и неоднозначные категории исключены. Минимум28 train-дат, coverage0.5, минимум14 train-наблюдений на позицию. Holdout-популярность, ошибки и продажи не участвуют в выборе. Это не сравнение всего ассортимента магазина.

День с любой транзакцией называется observed-store date, не подтверждённым открытым днём. Основная политика observed-store-zero предполагает0 для отсутствующей выбранной позиции в такой день после первой записи этой позиции. Это допущение: отсутствие строки может означать снятый ассортимент или отсутствие товара. До первой записи позиции нули не создаются. Даты без любых транзакций остаются неизвестными, а не закрытыми/нулевыми. Sensitivity missing исключает отсутствующие позиции, сохраняя только наблюдаемые продажи; вывод условен по этим датам. Разные политики имеют разные популяции и n, их MAE нельзя напрямую считать улучшением модели.

Поддержан только явно запрошенный rolling-one-day-ahead: дневные итоги предполагаются доступными после окончания дня; предыдущие факты validation/test могут стать лагами следующего дня. Без --history-mode запуск отклоняется. Фиксированного многодневного горизонта нет. Модель обучена только на train и не переобучается на validation/test; alpha1 и календарные лаги7/14 заранее фиксированы. Imputer/scaler/encoder обучаются на train. Неизвестный лаг получает численный0 и индикатор пропуска внутри pipeline; это не нулевая метка продаж.

B0/B1 используют общее численное ядро с явным value_key=item_line_count и eligibility; производственных полей нет. Для каждого validation/test периода все методы сравниваются на одном пересечении доступных date/item прогнозов. Отчёт показывает candidates, общий n, покрытие каждого метода, исключённые/предполагаемые нули, прогнозы по датам, pooled/per-item MAE и WAPE. WAPE=sum(abs(error))/sum(actual), ratio; при нулевом знаменателе null, не фиктивные0%. Минимум7 совместных дат на каждую из5 позиций в каждом периоде; иначе отказ с диагностикой. Семь дат — технический порог, не гарантия реальной точности.

## Проверяемый запуск без внешнего файла

Из корня checkout, Python3.14:

```powershell
.\.venv\Scripts\python.exe -m pip install -r tools/requirements.lock
.\.venv\Scripts\python.exe tools/evaluate_sales.py --csv fixtures/synthetic_sales_lines.csv --source synthetic-sales-only --history-mode rolling-one-day-ahead --test-end 2017-03-09 --output private/sales-demo/report.json
.\.venv\Scripts\python.exe -m unittest discover -s tools/tests -v
```

Этот публичный fixture полностью синтетический. Он проверяет исполнение, не качество на реальном магазине. CLI создаёт отсутствующие родительские каталоги. Для внешнего файла используйте --source external-sales-only, стандартные даты протокола и --expected-sha256 из sales_source.json:

```powershell
.\.venv\Scripts\python.exe tools/evaluate_sales.py --csv 'C:\private\bakery_sales_revised.csv' --source external-sales-only --history-mode rolling-one-day-ahead --expected-sha256 5f7e0af51f4bf985f0d2ac2e35209c94d2426726993b98d1c2e9d8bc145860ee --output 'C:\private\bread-sales-report.json'
```

Исходник и полный внешний отчёт остаются приватными; не добавляйте их в Git. Проблема CSV/хеша/параметров даёт понятную ошибку и exit2. Нехватка истории пишет status=refused и exit2. В отчёте нет выручки, потерь, экономии, производственной рекомендации или автоматического выбора рабочего метода. После просмотра test нельзя подбирать настройки и выдавать тот же test за независимый финальный: нужен новый заранее отделённый период.
